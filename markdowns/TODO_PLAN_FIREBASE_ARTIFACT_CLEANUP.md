# План очистки репозитория от Firebase-артефактов

## Цель и границы

Удалить из версии проекта всё, что нужно только для прежней Firebase-инфраструктуры, не затронув ни исходные снимки данных, ни средства переноса этих данных в PocketBase.

План **не разрешает удалять или редактировать** следующие группы:

- `backend/migration-data/**` — локальные экспортированные данные, репетиционные базы, карты идентификаторов и манифесты. В репозитории они уже игнорируются, но содержат персональные данные и являются источником миграции.
- `backend/tools/migration/**` — импортеры, снимки, тесты и документация миграции из Firebase в PocketBase.
- `restore/**`, в частности `restore/plan.json` — созданный средствами восстановления снимок/план восстановления; каталог игнорируется Git.
- Миграции PocketBase в `backend/internal/migrations/**`.
- Официальные экспортированные Firebase Auth/Firestore/Storage-файлы, если они находятся в разрешённом хранилище миграций. Их нельзя перемещать, публиковать или добавлять в Git в рамках этой работы.

Локальный файл `.secrets/aerun-forum-*.json` не отслеживается и не является частью истории Git. Его удаление, отзыв сервисного аккаунта и ротация ключа — отдельная операционная задача, требующая подтверждения владельца Firebase-проекта.

## Зафиксированная исходная инвентаризация

Ниже перечислены Firebase-артефакты, которые на момент составления плана отслеживаются Git и не входят в исключения:

| Группа | Пути | Действие |
| --- | --- | --- |
| Firebase CLI и хостинг | `.firebaserc`, `firebase.json`, `.firebase/` (локальный кэш, уже игнорируется) | Удалить конфигурацию из Git; кэш убрать локально только после подтверждения. |
| Правила Firebase | `firestore.rules`, `firestore.indexes.json`, `database.rules.json`, `storage.rules` | Удалить после контрольной проверки, что VPS/PocketBase не читает их при сборке или развёртывании. |
| Клиентская заглушка | `firebase.js` | Удалить, если поиск подтвердит отсутствие импортов; заменить оставшиеся импорты на PocketBase API до удаления. |
| Cloud Functions | `functions/**` (исходники, manifest и lockfile) | Удалить весь каталог. Это старое рабочее Firebase-приложение, не набор файлов миграции. |
| Корневые зависимости и команды | `package.json`, `package-lock.json` | Удалить `firebase`, `firebase-tools`, Firebase deploy-команды и `lint:rules`; обновить lockfile штатным пакетным менеджером. |
| Одноразовые Firebase-скрипты | `scripts/firestore-inspect.mjs`, `scripts/init-db.js`, `scripts/migrate-status-roles.js`, `scripts/backfill-*.js`, `scripts/clean-*.mjs`, `scripts/recompute-counters.mjs`, `scripts/restore-*.mjs` | Классифицировать по назначению до удаления: перенос/восстановление данных сохранить в архиве миграции; эксплуатационные Firebase-команды удалить. Нельзя удалять пакетно только по имени. |
| Документация и автоматизация | старые упоминания Firebase в `.github/**`, `backend/README.md`, npm-скриптах | Исправить только активные инструкции и ссылки. Исторические документы оставить, пометив их как архивные, если они нужны для трассируемости миграции. |

`src/**` уже работает через доменные PocketBase API; `firebase.js` содержит лишь no-op заглушки. Это надо подтвердить автоматическим поиском импортов непосредственно перед удалением.

## Последовательность работ

1. **Создать контрольную точку и реестр.**
   - Зафиксировать чистое состояние рабочей ветки, полный список отслеживаемых Firebase-путей и SHA-256 всех файлов в `backend/migration-data/**` и `restore/**`.
   - Создать в ветке отдельный реестр «сохранить» с путём, назначением и контрольной суммой. Не включать снимки и экспортированные данные в commit.
   - Утвердить для каждого скрипта из `scripts/**` один из статусов: `сохранить как миграционный`, `перенести в backend/tools/migration`, `удалить`.

2. **Убрать зависимости выполнения.**
   - Найти все импорты `firebase`, `firebase-admin`, `firebase-functions`, URL `firebaseio.com` и обращения к Firebase CLI, исключая `node_modules`, `backend/migration-data/**` и `backend/tools/migration/**`.
   - Для каждого живого вызова подтвердить PocketBase-эквивалент и покрыть критический поток (авторизация, запись, уведомления, загрузка аватара) проверкой или тестом.
   - Удалить неиспользуемую `firebase.js` только после нулевого результата поиска её импортов.

3. **Удалить Firebase-код и конфигурацию.**
   - Удалить `functions/**`, `.firebaserc`, `firebase.json`, `firestore.rules`, `firestore.indexes.json`, `database.rules.json`, `storage.rules` и подтверждённые не-миграционные скрипты.
   - Удалить из `package.json` Firebase зависимости, команды `deploy:test`, `deploy:prod`, `lint:rules` и связанные с ними части `lint`; затем регенерировать `package-lock.json`.
   - Не менять `deploy:vps*`, `deploy.py`, PocketBase-конфигурацию и миграционные инструменты.

4. **Привести документацию и защитные проверки в соответствие.**
   - В активных руководствах описать единственный поддерживаемый путь: Vite + Go/PocketBase + VPS.
   - Явно обозначить `backend/tools/migration/README.md` как единственное место для legacy Firebase-источника и запуска миграционных процедур.
   - Удалить либо переписать проверки, которые ищут Firebase-реализацию, но сохранить проверки, защищающие от её повторного появления. Минимальная постоянная проверка должна падать при появлении Firebase пакетов в production-зависимостях, Firebase CLI в npm-скриптах или импортов Firebase вне разрешённых миграционных путей.
   - Уточнить `.gitignore`: оставить исключения для `.secrets/`, `.firebase/`, старых логов и миграционных снимков, чтобы случайно не закоммитить персональные данные после очистки.

5. **Проверить результат до слияния.**
   - Выполнить `npm run lint:js` и `npm test`; Firebase-эмуляторы и `firebase deploy` не запускать.
   - Выполнить `go test ./...` из `backend` и дождаться зелёного отчёта backend CI после push.
   - Проверить `rg -i "firebase|firestore|firebaseapp|firebaseio"` по отслеживаемым файлам. Допустимые совпадения: только документы об истории, `backend/tools/migration/**`, `backend/migration-data/**` (если локально доступен) и выбранные тесты-запреты.
   - Проверить `git diff --check`, `git status --short`, отсутствие Firebase-пакетов в корневом lockfile и успешную локальную сборку фронтенда, если её запуск отдельно разрешён владельцем.



## Критерии готовности

- В корне нет Firebase CLI-конфигурации, правил, SDK/CLI-зависимостей и Firebase deploy-команд.
- Каталог `functions/` и не-миграционные Firebase-скрипты отсутствуют.
- В рабочем коде и активных инструкциях нет обращения к Firebase.
- Все исключённые снимки и миграционные файлы сохранились с теми же путями и контрольными суммами.
- Линтер, frontend-тесты, backend-тесты и backend CI успешны.
- Исторические упоминания Firebase либо находятся внутри миграционных/архивных материалов, либо явно помечены как legacy-контекст.

## Откат

Изменения выполнять одним или несколькими атомарными commit'ами, отделяя удаление Firebase-артефактов от редакции документации. Откат — `git revert` соответствующего commit'а; снимки и локальные базы не должны быть частью этого механизма и не должны удаляться ради «чистого» рабочего дерева.
