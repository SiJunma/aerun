## Разбор предложения «новый диалог-оболочка с датой» (2026-10-13)

### Что предлагает владелец
- У себя: cleared_at = горизонт (как сейчас).
- Оболочка: при новом сообщении после удаления — создать НОВЫЙ conv с тайтлом «диалог от <дата>».
- У собеседника: тоже открывается как новый диалог.

### Почему это ломает текущую модель (важно)
1. **Спека сейчас — один диалог на пару (горизонт), а не пачка оболочек.** `PROJECT_SPEC.md:455`: удаление = «скрывает все сообщения до текущего момента» у себя; «второй собеседник сохраняет всю историю»; «переписка для первого откроется как пустая, начиная с последнего сообщения». Т.е. задумка была: conv один, cleared_at режет видимость. Новый conv на каждое «удалил → написал» — это смена модели, а не фикс D5.
2. **Тайтл «диалог от числа» сейчас некуда показать.** Inbox-строка (`DirectMessages.jsx ~L1013-1057`) рендерит `participantNames[peerUid]`, а не `conv.title`. Title пишется при `POST /dms` (`theirProfile.nickname`), но в UI не используется. Чтобы различать оболочки, придётся менять рендер строк (показывать title/дату) — иначе у обоих юзеров будет просто два одинаковых «User».
3. **У собеседника будет ДВА видимых диалога.** Peer ничего не удалял → его `cleared_at` пуст → старый conv с историей + новый пустой conv оба проходят фильтр списка (`dms.go ~L920`). Получаем ровно симптом D4 («два одинаковых чата»), но уже штатно. Чтобы этого не было, надо при создании «оболочки» прятать/архивировать старый conv и у пира — а это уже операция над чужими данными (собеседник историю не удалял, а мы её спрячем).
4. **Peer-lookup сейчас возвращает самый свежий conv с пиром** (`ORDER BY last_message_at DESC LIMIT 1`). С пачкой оболочек он начнёт возвращать то старый, то новый в зависимости от `last_message_at` — D4-гонка усугубится, а не исчезнет. Нужен новый контракт: «активный» vs «архивный».
5. **D5 чинится без новой сущности.** Гипотеза S3 (строгое `>` + секундная точность `cleared_at` vs `created`/`last_message_at`) объясняет все три подсимптома одной строкой. Фикс — граница/точность/sequence вместо времени + `refreshDmList` на фронте. Это день, а не редизайн.

### Вывод (мнение, не решение)
- Смысл в идее есть только если цель — «история удалённого диалога никогда не смешивается с новой» как в Telegram-папках. Но цена: новый контракт список/peer-lookup, миграция/архивация старых conv у пира, редизайн строк inbox, риск размножения диалогов (D4 станет фичей).
- Дешевле и ближе к спеке: оставить ОДИН conv + горизонт, починить границу `>` и мгновенное обновление списка. Разделитель «Диалог очищен <дата>» в ленте даст тот же UX «начали с чистого листа» без второй оболочки.
### Решение владельца (2026-10-13): вариант A
- Один диалог + горизонт cleared_at, чиним границу времени. Оболочки не делаем.
- S3 остаётся как есть. Работаем по шагам S0→S6.

## S7 — приёмка владельца 2026-10-14: отправленное не рисуется (D6)

### Симптомы (ручной проход по UI, два аккаунта)
1. Удалила диалог с участником → из профиля открыла новый → написала → отправила. Лента пуста, строки в списке диалогов нет.
2. Релоад → новый диалог и отправленное сообщение на месте. Пишу второе → снова не появляется.
3. «Сообщения не отрисовываются сразу — это баг всех диалогов» (не только после clear).

### Причина (D6) — у автора нет delivery path для СВОЕЙ отправки
Три факта по одному из каждого слоя; их композиция и даёт баг:
- `handleSend` (`DirectMessages.jsx`) делал `await sendDmMessage(...)` и **выбрасывал ответ**: ни append в `messages`, ни `refreshDmMessages`, ни `refreshDmList`.
- Сигнал `dm.post` адресован только собеседникам: `publishDMSignalToPeers` исключает вызывающего (`dms.go:353`), а `sendDMMessageHandler` публикует по `otherMembers` (`dms.go:793`). Автор своего сообщения сигнала не получает никогда.
- `shared-poll`: realtime CONNECTED → таймер УДАЛЁН (`onConnected → stopTimer()`, `shared-poll.js:330`), событие для этого не нужно. Сид с работающим стримом не имеет ни 30s-тика `dm-messages`, ни 10s-тика `dm-list`.
Итог: собственная отправка видна только после релоада (свежий монтаж = свежий read) — в ЛЮБОМ диалоге, что совпадает с «баг всех диалогов». А clear → отправка из профиля не возвращает строку диалога в список: серверный фильтр `last_message_at > cleared_at` (`dms.go:949`) скрывает её до тех пор, пока list-read не увидит новое сообщение, а list-read никто не дёрнул. Ровно та же дыра, что чинили для edit/delete (`applyMessageUpdate` + `refreshDmMessages`) — send-путь просто не получил тот же фикс.

### Фикс (минимальный, по шаблону edit/delete)
- `src/api/dms.js`: `sendDmMessage` возвращает `normalizeDmMessage(res.message)` — контракт «мутация возвращает строку, которую записала».
- `DirectMessages.jsx` `handleSend`: capture ответа → append в `messages` (merge по id, сортировка по `sequence` — тот же компаратор, что в poll-callback) → `refreshDmMessages(activeChatId)` → `refreshDmList(myUid)`.
- `scripts/check-dm-mutation-state.mjs`: gate расширен на send (`sendDmMessage` в цикле возврата строки; новый блок для `handleSend`: capture + `setMessages` + оба refresh); счётчик `normalizeDmMessage` ≥ 6.
- Чекпоинт: отправка в любом диалоге рисует пузырь сразу; clear → отправка из профиля → строка в списке И сообщение в ленте без релоада. `npm test` зелёный.
