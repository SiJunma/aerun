# Концепт: Удалённый пользователь (Deleted User) — профиль, посты, репутация, ЛС

**Дата:** 2026-10-18  
**Статус:** Реализовано и проверено (аудит 2026-10-19: дефекты D1–D11
исправлены, полный `go test ./internal/...` зелёный, CI-шаги `gofmt`/`build`/
`vet` проходят). Открытым остаётся только пункт D3 — гонка в подсистеме ЛС,
не в soft-delete (решение за владельцем).

## АУДИТ РЕАЛИЗАЦИИ (2026-10-19) — что проверено, что найдено

Проверка выполнена по коммиту `7a29f17` ("Soft-delete deleted users: profile,
posts, reputation, DMs") чтением кода, прогоном тестов и сверкой с
`.agent/rules/AGENTS.md` (правило «Deletion Must Settle Its Denormalized
Copies», «Zero Silent Failures», «сначала доказательство, потом утверждение»).

### Итог: подход выбран правильный, но реализация неполна

Пять решений — правильные, и их стоит сохранить:

1. **Soft-delete вместо хард-удаления строки.** Правильный ответ на исходную
   проблему: посты и профиль удалённого должны продолжать рендериться, а
   строка `users` — оставаться носителем запечённых данных.
2. **`status = "deleted"` ВНЕ `AllStatuses()`.** Deny-by-default через
   `NarrowForStatus`: значение нельзя назначить через форму статуса, но
   можно найти фильтром. Правильное разделение двух словарей
   (`AllStatuses` — назначаемые, `AllStatusValues` — хранимые).
3. **Три координатные записи в одной транзакции** (`is_deleted`, `status`,
   очистка `nickname_normalized`) — ник не теряется, но освобождается для
   повторной регистрации.
4. **Очистка `nickname_normalized` через raw `UPDATE`, а не `Set`+`Save`.**
   Обоснование верное: поле REQUIRED, и `Save` с пустым значением отвергли бы
   валидацией («cannot be blank»). Сырой `UPDATE` — правильный инструмент
   (так же работает `backfillUserLastSeen`). **Но** у этого решения есть
   побочный эффект, который автор не увидел: строка после этого становится
   несохраняемой — см. D1. Правильный путь — снять `Required` с поля
   (миграция `1770000010`), и тогда `Set`+`Save` работает.
5. **`purgeUserContent` идёт через те же пути остатков**, что и обычные
   удаления (`purgeTopicResidue` / `deleteTopicPosts` / выплаты репутации), а
   не через отдельную «упрощённую» ветку. Это прямое требование правила
   «Deletion Must Settle Its Denormalized Copies».

### Найденные дефекты (все — реальные, не стилистические)

#### D1 (БЛОКЕР). Очищенная `nickname_normalized` делает строку несохраняемой

`users.nickname_normalized` — **REQUIRED** TextField (миграция `1766000000`).
Soft-delete затирает его в `''` сырым `UPDATE`, обходя валидацию. Но после
этого **любая последующая запись в ту же строку падает**:

```
SECOND SAVE FAILED: nickname_normalized: cannot be blank.
```

(воспроизведено пробным тестом: soft-delete → `Save` с изменённым
`posts_count` → отказ валидации).

Кто это задевает: `adjustUserReputation` / `adjustUserPostCount` /
`adjustUserTopicCount` → `applyUserCountDelta` → `txApp.Save(user)`. Любой
поздний сдвиг счётчика удалённого пользователя (например, когда модератор
позже удалит один из его постов, или при `RecomputeUserCounters`) упадёт
с 500. То есть soft-delete «заливает» строку, и обслуживание приведённых
значений становится невозможным.

**Как правильно.** Не обходить валидацию, а снять с поля требование
`Required` — одной новой миграцией, как это уже сделано для `dm_messages.text`
в `1767900000` («text is relaxed to optional… the schema now states what the
tombstone actually is»). Пустая `nickname_normalized` — законное состояние
(ник освобождён), и поле обязано его допускать. Тогда `nickname_normalized`
можно писать обычным `Set("")` + `Save`, без сырого `UPDATE`, и счётчики
остаются обслуживаемыми.

#### D2 (БЛОКЕР). `gofmt` не проходит — CI красный

`gofmt -l .` в `backend/` возвращает три файла:

```

internal\platform\pocketbase\forum_posts.go
internal\platform\pocketbase\user_soft_delete_test.go
```

Первый шаг CI (`gofmt`) падает, поэтому пайплайн останавливается, и в

«go build, npm run build… pass» проверку `gofmt` не покрывает.

#### D3 (БЫЛО БЛОКЕРОМ — ЗАКРЫТО). `clearConversationHandler` ронял чужой тест

Полный прогон пакета даёт:

```
--- FAIL: TestClearedConversationShowsTheNextMessageImmediately (1.77s)
    dm_inbox_participants_test.go:422: thread must show exactly the
    post-clear reply, got {"oldest_sequence":0,…,"items":[],"has_more":false}
```

**Уточнение после проверки (это важно, чтобы не обвинить невиновного):**
прогон на РОДИТЕЛЕ коммита (`7a29f17^`, worktree) падает ТОЖЕ — 1 из 30.
Значит это **не регрессия soft-delete**, а давняя гонка, которую коммит
подсветил (он переписал соседний код `clearConversationHandler`).

Истинная причина (доказана пробным тестом, 2 из 30): фильтр
`created > cleared_at` сравнивает **миллисекундные** таймстемпы, а сообщение,
отправленное сразу после clear, может получить ту же миллисекунду, что и
предыдущее сообщение. Проба показала:

```
msg seq=1 created="2026-10-19 14:02:20.506Z"
msg seq=2 created="2026-10-19 14:02:20.506Z"   <- тот же миллисекунд
member cleared_at="2026-10-19 14:02:20.506Z"
=> seq=2 отфильтрован: created > cleared_at ложно
```

Якорь к `last_message_at` (исправление D5) помогает, когда новое сообщение
получает БОЛЬШУЮ миллисекунду; при равенстве он не спасает.

**ЗАКРЫТО** (см. «Что реализовано», пп. 3–4): горизонт переведён с
таймстемпа на `sequence` — монотонный и без ограничения разрешения. «Скрыто
всё с `sequence <= N`» становится точным, и гонка исчезает полностью, а не
становится реже. Тест
`TestClearedConversationShowsTheNextMessageImmediately` проходит стабильно,
новый `TestDMClearHorizonIsExactOnSequence` фиксирует контракт.

#### D3a (БЫЛО — ЗАКРЫТО). Регрессия в `clearConversationHandler` всё-таки есть — в комментарии

Сам код horizon'а коммит `7a29f17` **не менял** (проверено `git diff`: изменены
только комментарий и добавлен вызов `dropConversationWithDeletedPeer`). Но
комментарий, который теперь стоит над функцией, **потерял объяснение** того,
почему якорь именно такой («A conversation with no messages yet clears to
"now" — there is nothing to anchor to»). Следующий читатель увидит
«not the wall clock» без причины и может «упростить» обратно к `NowDateTime()`
— ровно та регрессия, которую тест ловит. Комментарий — часть контракта
здесь, и он должен остаться полным.

#### D4 (СУЩЕСТВЕННО). Живая сессия удалённого не «мертва» полностью

Пункт «Осталось» ниже утверждает: «`requireNotBanned` теперь отказывает с
403 на **любую** мутацию (пост/тема/почта) — сессия мёртва». Фактически
`requireNotBanned` стоит в **8** местах (`account_credentials.go` ×3,
`forum_posts.go` ×2, `forum_topics.go` ×2). Остальные мутации удалённого
аккаунта с живым токеном проходят:

- `createPostHandler` / `createTopicHandler` — **создание** контента. Данные
  записи создаются по `e.Auth.Id`; проверки статуса там нет вовсе, а
  `categoryWriteAllowed` смотрит только на `StatusBanned` (и на `RoleRoot`).
  `NarrowForStatus` обнуляет права, но `categoryWriteAllowed` при явном
  списке ролей категории отвечает `slices.Contains(override, acc.Role)` —
  то есть **отдаёт доступ по списку ролей, минуя обнулённые права**.
- `updateMyProfileHandler`, `updateSettingsHandler`, `uploadMyAvatarHandler`,
  `requireCharacterAuthor` — проверяют только `StatusBanned`.
- `upsertDraftHandler` / `publishDraftHandler` — статус не проверяется.
- `editDMMessageHandler` / `deleteDMMessageHandler` — статус не проверяется.

**Как правильно.** Не «добавить ещё 15 проверок», а закрыть корень: сделать
`StatusDeleted` запретом наравне с `StatusBanned` в **одном** месте.
`NarrowForStatus` уже обнуляет права, но статус проверяется точечно. Чистое
решение — единый предикат и проверка в общем слое (middleware) для всех
мутационных маршрутов, а не в каждом хендлере. Тогда «сессия мёртва» станет
свойством маршрута, а не перечислением.

#### D5 (СУЩЕСТВЕННО — ЗАКРЫТО). `delete_posts` оставлял у выживших постов «мёртвую» репутацию

**Первоначальная гипотеза (двойная выплата) НЕ подтвердилась** — и это
проверено пробным тестом, а не рассуждением. Реальный дефект другой и
подтверждён:

`purgeUserProfileVotes` удаляет голоса, **отданные** удалённым (`voter_id`),
и выплачивает обратно репутацию **получателя** (`adjustUserReputation(targetID,
-value)`). Но у голоса есть **две** денормализованные копии: счётчик
`users.reputation` получателя И счётчик `posts.reputation` самого поста.
Обычный путь отзыва голоса (`deleteReputationHandler`) двигает **обе**:

```go
targetUser.Set("reputation", targetUser.GetInt("reputation")-val)
if postID != "" {
    post.Set("reputation", post.GetInt("reputation")-val)
}
```

В пуре двигается только первая. Проба (удалённый member голосует на пост
ВЫЖИВШЕГО автора; после пура пост и голос исчезают/остаются):

```
BEFORE purge: post.reputation=5  pending.reputation=5
AFTER purge:  post.reputation=5  pending.reputation=0
=> post.reputation должно стать 0 (его голоса больше нет)
```

Итог: `users.reputation` сходится, а `posts.reputation` у выжившего поста
**зависает с голосом, которого больше не существует**. Это прямое нарушение
правила репозитория «Deletion Must Settle Its Denormalized Copies»: при
пересчёте (`RecomputeUserCounters`) посты и пользователи разойдутся.

**Как правильно.** В ветке «cast» (`voter_id = userID`) двигать оба счётчика,
как это делает `deleteReputationHandler`: уменьшать `posts.reputation` поста,
если такой пост ещё существует.

#### D6 (СУЩЕСТВЕННО). Два разных механизма одного правила

403 на удалённого цель в `voteUserHandler`/`votePostHandler` реализован
через `isUserDeleted(targetUser)` внутри `runCommand` — то есть отдельной
реализацией того же правила, что и в `requireNotBanned`. Само по себе это
работает, но оставляет две реализации одного правила в двух слоях — источник
будущего расхождения (одну легко забудут обновить).

#### D7 (СУЩЕСТВЕННО). `isUserDeleted` и SQL-фильтры проверяют разные вещи

`isUserDeleted()` возвращает true при `status == "deleted"` **ИЛИ**
`is_deleted`. А SQL-фильтры в `checkNicknameHandler`, `registerHandler`,
`searchUsersHandler`, `listUsersHandler` проверяют **только** `is_deleted`.
Для строки, удалённой бинарником без новой колонки (ровно тот случай,
который `isUserDeleted` комментирует как поддерживаемый), ник останется
занятым. Несоответствие двух предикатов об одном понятии.

#### D8 (СУЩЕСТВЕННО — ЗАКРЫТО). Админ-таблица показывала удалённого аккаунта как живого

`adminListUsersHandler` отдаёт `"role": record.GetString("role")` и
`"status": record.GetString("status")` — для удалённого это «сырое» значение
(например `player`) и `status: "deleted"`. **Фронт этот вердикт не
рисовал:** в `AdminPage.jsx` бейдж статуса выбирался так:

```jsx
{u.status !== 'pending' && u.status !== 'banned' && <Badge bg="success">Active</Badge>}
```

`deleted` не равно ни `pending`, ни `banned` — значит удалённый аккаунт
**показывался в админ-таблице зелёным бейджем «Активен»**. Таблица штаба
говорила, что удалённый аккаунт жив, — ровно то, чего она говорить не
должна. Кроме того, кнопки «Забанить» / «Удалить» оставались доступны, хотя
сервер отвечает на них 409.

**Как правильно (ПО РЕШЕНИЮ ВЛАДЕЛЬЦА от 2026-10-19).** Удалённого
аккаунта в админ-таблице **нет вообще** — таблица штаба перечисляет
аккаунты, которые ещё могут действовать, а удалённый не может ничего.
Поэтому `adminListUsersHandler` исключает удалённых из выдачи по умолчанию
(тем же предикатом `notDeletedUsersExpr`, что и публичная доска), а
`?status=deleted` остаётся как СОЗНАТЕЛЬНЫЙ точечный запрос штаба
(«проверить, что за собой не оставил»), а не часть списка.

Бейдж «Удалён» в таблице и кнопки действий для удалённых убраны — такой
строки в общем списке нет, и рисовать её было бы правдой только наполовину.
`role` в админском ответе остаётся СОХРАНЁННЫМ: это история «кем аккаунт
был, пока мог действовать», и её читает редактор ролей.

#### D9 (СУЩЕСТВЕННО). `verifyDeletedUserSchema` не описывает обратный сценарий

Проверка на `OnServe` — правильная идея (fail-fast). Но она требует, чтобы
`users.is_deleted` существовал; для базы, где удаления уже выполнялись
старым бинарником (хард-delete), колонки не будет, и процесс не стартует.
Сообщение об ошибке упоминает только рассинхрон бинарника и каталога данных,
но не упоминает сценарий «данные удалены старым способом, нужна миграция
данных».

#### D10 (МЕЛОЧЬ, но по правилам репозитория важно). Рассинхрон словарей

`auth.AllStatusValues()` включает `"deleted"` и используется в трёх местах с
разным смыслом: список значений поля `status` (миграция), фильтр админ-списка,
`sel.Values` в `1770000009`. При этом `AllStatuses()` — без `"deleted"`. Пока
это так, любая будущая правка одного словаря без другого даст
«полу-удалённую» строку. Стоит зафиксировать инвариант тестом: в `auth`
уже есть `TestDeletedStatusIsStoredButNotAssignable` (проверяет
неприсваиваемость), но нет проверки, что `AllStatusValues` ⊇ `AllStatuses`
и что `"deleted"` присутствует ровно в одном словаре.

#### D11 (МЕЛОЧЬ). Дубликат секции и опечатка в заголовках

Блок «## Фронтенд (пп. 10–13 концепта) — ВЫПОЛНЕНО» повторён дважды
идентично. Также в заголовках混入 китайские иероглифы `概念` — опечатка
автора (`пп. 10–13 концепта`).

### Что сделано правильно, но требует решения владельца

- `dropConversationWithDeletedPeer` — хорошее решение по смыслу (нет живых
  читателей → диалог можно убрать), но оно **жёстко удаляет** сообщения
  (`txApp.Delete(msg)`), тогда как по правилу репозитория «удаление для ЛС —
  МЯГКОЕ (tombstone)»: «оба участника должны продолжать видеть, что сообщение
  было и что оно говорило». Здесь сообщения исчезают бесследно. Нужно
  решение владельца: tombstone вместо удаления, либо явная фиксация, что
  «clear у удалённого собеседника» — это удаление.
- `dropConversationWithDeletedPeer` считает «нет живых читателей» и по
  участникам **без строки** в `users` (orphans после старого хард-удаления) —
  правильно, это закрывает дыру из `DONE_GHOST_USER_CLEANUP…`.
- `adminDeleteUserHandler` пишет `delete_posts` в `audit` всегда, и
  повторное удаление даёт 409 — правильно. Но `_ = recordAuditLog(...)`
  глушит ошибку аудита (тот же стиль, что и в предыдущем коде).
- `getUserProfileHandler` отдаёт удалённому профилю полный набор полей
  (`bio`, `location`, `contacts`, `birthday` …). Концепт (п. 10) требует
  «только текст „Этот аккаунт удалён“; статуса, роли, локации и прочего —
  нет». Фронт скрывает это через `isLimitedProfile`, но API отдаёт данные,
  которые по концепту показываться не должны.

## РЕШЕНИЯ ВЛАДЕЛЬЦА (2026-10-19) — фидбек и принятые решения

Владелец пересмотрел три пункта и дал новый контекст по ЛС. Ниже — ответы
аудита и решения, принятые для реализации.

### 1. Сессия удалённого пользователя должна умирать ТУТ ЖЕ

**Что уже сделано (D4):** delete-handler крутит `tokenKey` аккаунта. PocketBase
подписывает токен `tokenKey + AuthToken.Secret` и проверяет подпись по
ТЕКУЩЕМУ `tokenKey` при каждом запросе (`core/record_query.go`: `secret :=
record.TokenKey() + baseTokenKey`), поэтому ротация ключа мгновенно обесценивает
и access-токен, и refresh-токен. Плюс общий гейт `requireLiveAccount` на
группе `/api/aerun` (403 на любую мутацию).

**Чего не хватало (и будет сделано):** серверная смерть сессии не приводит к
логическому выходу в клиенте. Токен в браузере остаётся в `authStore`, запросы
начинают падать, но пользователь видит «пустой форум» вместо объяснения. Это
ровно тот «silent failure», который запрещает `.agent/rules/AGENTS.md`
(«Zero Silent Failures») — тем более что для ЗАБАНЕННОГО аккаунта механизм
уже есть (`banned_logout` + модалка в `GlobalModals`), а для удалённого его
нет.

**Решение:** клиент при `profile.status === 'deleted'` повторяет путь бана —
пишет флаг, разлогинивает и показывает модалку с объяснением «аккаунт
удалён», а не «доступ заблокирован». Плюс: `sendApi` на 401/403 от удалённого
аккаунта инициирует тот же выход, чтобы сессия не «висела» до первого
перечитывания профиля.

### 2. Удалённый пользователь НЕ должен показываться в админ-таблице

Это решение владельца меняет D8: бейдж «Удалён» в админ-таблице НЕ нужен,
потому что такой строки там быть не должно.

**Решение:** `adminListUsersHandler` исключает удалённых из выдачи по
умолчанию (как публичная доска), а фильтр `?status=deleted` — единственный
способ их увидеть — остаётся (штаб должен уметь найти удалённый аккаунт, иначе
нечем проверить «а не осталось ли его контента»). Права на запись у удалённого
по-прежнему 409.

Итог по D8: строки удалённых в общем списке админки нет, бейдж «Удалён» в
таблице не рисуется, кнопок действий для них нет. `?status=deleted` —
точечный инструмент штаба, а не часть списка.

### 3. ЛС: папки «Инбокс» и «Удалённые», мягкое vs жёсткое удаление

**Принятый контекст владельца:**
- удаление чата → чат уходит в папку «Удалённые» (мягко);
- удаление в папке «Удалённые» → удаление по харду, необратимо — **при условии,
  что читателей не осталось**;
- если пользователи удаляли чаты в разные моменты, потом начали новые, а потом
  удалили чаты в «Удалённых» — **хардово удаляются только те сообщения,
  которые точно больше никогда не будут прочитаны**.

**Что из этого следует технически (и почему текущая модель не годится):**

Сегодня «удалить чат» — это `POST /dms/{id}/clear`, который ставит
`dm_members.cleared_at` и прячет переписку у ОДНОГО участника. Это уже
мягкое удаление, но папки «Удалённые» нет, и хардового удаления нет вовсе.
Зато есть ровно то, что владелец описал как проблему: `dropConversationWithDeletedPeer`
удаляет переписку **по харду целиком** (включая сообщения), когда все прочие
участники удалены — а по правилу репозитория «удаление для ЛС — МЯГКОЕ
(tombstone)» сообщения должны остаться видимыми.

**Ключевой инвариант, который делает модель сходимой:**

> Сообщение можно удалить по харду **только если ни один участник, который
> ещё может его прочитать, не сможет его прочитать**. Иначе хардовое удаление
> отняло бы у живого участника историю.

Поэтому «читателей не осталось» — это не «все удалили», а «у каждого
участника, который ещё может читать, этот кусок уже скрыт». Отсюда и
сформулированное владельцем «хардово удаляем только те сообщения, которые
точно больше никогда не будут читаться».

**Реализация (согласовано с владельцем по смыслу):**

1. **Папки.** `GET /api/aerun/dms?folder=inbox|deleted`. «Инбокс» — текущий
   список чатов; «Удалённые» — чаты, которые этот участник УДАЛИЛ (мягким
   шагом). Разделение — per-member, потому что метки живут в `dm_members`
   (у каждого участника своя).
2. **Три шага, а не два.** Разведение «мягко vs хардово» требует трёх
   действий, иначе «мягкое удаление» и «удаление в папку» — одно и то же:
   - `clear` (`POST /dms/{id}/clear`) — спрятать от себя прочитанное. Чат
     остаётся в инбоксе и возвращается с новым сообщением.
   - `delete` (`POST /dms/{id}/delete`) — переложить чат в «Удалённые».
     Мягко: переписка остаётся, собеседник её читает.
   - `erase` (`DELETE /dms/{id}`) — удалить безвозвратно, но ТОЛЬКО то, что
     больше никто прочитать не может. Пока кто-то может — 409 с причиной,
     а не «сделано наполовину».
3. **Мягкое удаление сообщения** (существующий `DELETE /dm-messages/{id}`)
   остаётся tombstone'ом: сообщение теряет текст, но остаётся видимым.
4. **Хардовое удаление перестаёт быть само-собой.** Раньше
   `dropConversationWithDeletedPeer` удалял переписку по харду целиком, как
   только все прочие участники были удалены, — в обход правила репозитория
   «удаление для ЛС — МЯГКОЕ (tombstone)». Теперь это решение самого
   участника, явным третьим шагом, и только для прочитанного всеми.

**Что это даёт против текущего кода:** «удалить чат» перестаёт быть необратимым
действием, а становится перемещением в «Удалённые»; необратимость появляется
явным следующим шагом и только там, где она безопасна. Это ровно разделение
«мягко vs хардово», о котором говорит владелец, и оно снимает противоречие с
правилом репозитория про tombstone.
### 4. Порядок сообщений в ЛС — `sequence`, одновременность не страшна



**Принято и снимает D3.** Владелец подтвердила: порядок в ЛС определяется
`sequence`, и то, что два сообщения могут прийти в одну миллисекунду и
получить «почти случайный» порядок — не страшно.

Это ровно то наблюдение, которое стоило за D3, но оно указывает на ДРУГОЕ
исправление: страшно не то, что порядок «почти случайный», а то, что фильтр
`created > cleared_at` **сравнивает миллисекундные таймстемпы** и при равенстве
прячет сообщение. Правильный инструмент здесь — `sequence`, который
монотонен и точен: «скрыто всё с `sequence <= N`» не зависит от часов.

**Решение:** горизонт «прочитанного» в ЛС переводится с таймстемпа на
`sequence`. Тогда:
- «прочитал до N» = `last_read_sequence` (уже есть, это `NumberField`);
- «удалил чат» = отдельная отметка, а не таймстемп;
- фильтр видимости становится `sequence > N` — **гонка исчезает полностью**,
  а не «становится реже».

Итог: D3 закрывается не заплаткой, а переходом на уже принятую в проекте
модель ordinal'ов (миграция `1767900000` прямо называет это «DM ordering
genuinely needs a stable ordinal»). Тест
`TestClearedConversationShowsTheNextMessageImmediately` станет детерминированным.

### Порядок реализации

1. Сессия удалённого умирает на клиенте (п. 1) + админ-таблица без удалённых (п. 2).
2. ЛС: горизонт на `sequence` + папки «Инбокс»/«Удалённые» + жёсткое удаление по
   правилу «нет читателей» (пп. 3–4).

### Что реализовано

**П. 1 — сессия умирает тут же (две стороны).**
- *Сервер:* delete-handler крутит `tokenKey` — токен аккаунта перестаёт
  проверяться, поэтому и access-, и refresh-токен мертвы сразу. Плюс общий
  гейт `requireLiveAccount` на группе `/api/aerun` (403 на любую мутацию).
- *Клиент:* `AuthProvider` выводит удалённый аккаунт тем же путём, что и
  забаненный (`sessionStorage['deleted_logout']` → `logout(true)`), и
  `GlobalModals` показывает модалку «Аккаунт удалён» (новая
  `DeletedLogoutModal`, ключи `auth.deleted_logout_title/_message`, en+ru).
  `sendApi` дополнительно гасит сессию на 401 — иначе участник сидел бы на
  форуме, который молча отказывает во всём, не объясняя почему.

**П. 2 — удалённого нет в админ-таблице.**
`adminListUsersHandler` исключает удалённых из выдачи по умолчанию (тот же
предикат `notDeletedUsersExpr`, что и публичная доска). `?status=deleted`
остаётся — это сознательный точечный запрос штаба («проверить, что за
собой не оставил»), а не часть списка. Бейдж «Удалён» в таблице и кнопки
действий для удалённых убраны: такой строки в общем списке нет.

**Пп. 3–4 — ЛС: три шага и два горизонта.**

| Шаг | Маршрут | Что делает |
|-----|---------|-----------|
| clear | `POST /dms/{id}/clear` | Прячет от участника всё, что он уже видел. Чат остаётся в инбоксе и возвращается с новым сообщением. |

  таймстемпам. Новая миграция `1770000011_dm_member_sequences` добавляет
  `cleared_sequence` и флаг `deleted`, и **переносит** старые значения из
  `cleared_at` (по `MAX(sequence)` среди сообщений, чей `created` не позже

- **Папки.** `GET /api/aerun/dms?folder=inbox|deleted`. Разделение

  держать один чат в разных папках — ровно то состояние, которое описала
  владелица.
- **Правило «нет читателей».** Граница стирания — **низший** горизонт среди
  живых участников: сообщения до неё не видит никто, их и стирают. Два
  вида участников границу **не держат**: ушедший навсегда (soft-deleted
  аккаунт — он не может войти) и тот, кто перенёс чат в свою «Удалённые» (он

  участника, явным вторым шагом, и только для прочитанного всеми.
- **Фронт.** В шапке списка ЛС — переключатель «Инбокс / Удалённые»; кнопка

  безвозвратно» и предупреждение о необратимости). Клиентский фильтр списка
  больше не решает за сервер, в какой папке чат (иначе чат из «Удалённых»
  пропадал бы по локальным таймстемпам).

## Запекание масок удалённого аккаунта (2026-10-19)

**Правило владельца:** если посты остаются на форуме, то посты, написанные
под маской, сохраняют эту маску — **ник, статус, аватар, подпись**.

Прежнее поведение было обратным: `decorate*` для удалённого аккаунта
возвращались раньше `applyMask`, и пост, который читался как «Rough», после
удаления аккаунта начинал читаться как «Удалённый пользователь». Форум
переписывал историю по дороге наружу.

**Почему это честно.** Маска в момент удаления аккаунта **заморожена**, и
заморозка обеспечивается тремя независимыми средствами:

1. удалённый аккаунт не может ходить — `requireLiveAccount` отказывает в
   любой мутации, а `tokenKey` ротируется при удалении;
2. маску, на которую ссылаются посты, удалить нельзя — команда удаления
   отвечает 409 («this character is used by posts»);
3. Staff не может ни переименовать такую маску, ни заменить её аватар —
   `requireMaskNotFrozen` отказывает 403: переименование маски задним
   числом переписало бы уже опубликованные посты.

Значит, строка маски остаётся и хранит ровно те данные, под которыми пост
был опубликован. Копировать их в сам пост не нужно: заморозка и есть
запекание.

**Маска, на которую постов нет, не запекается.** Ничего не отображается —
значит, ничего не может быть переписано, и её заморозка оставила бы строку
навечно: владельца нет, а staff не смог бы её убрать. Такую маску staff
удалить может (и это единственный способ её убрать).

**Что поменялось в коде:**

- `decoratePostAuthor`, `decorateTopicAuthor`, `decorateLastPostAuthor` —
  `applyMask` / `applyLastPostMask` теперь вызываются **до** раннего выхода
  для удалённого аккаунта, а не после;
- `topicPayload` — маска автора темы больше не отбрасывается, если аккаунт
  удалён;
- `requireMaskNotFrozen` — правка и аватар запечённой маски отвергаются
  (403).

**Что НЕ меняется:** аккаунт остаётся удалённым. Маска — слой отображения
над личностью, а личность исчезла: `author_deleted: true`,
`author_role_id: "Deleted"`, в DTO `deleted: true` и `user_id` удалённого
аккаунта. Профиль недоступен, ЛС и цитирование — по-прежнему недоступны.
Маска не воскрешает аккаунт.

**Тесты:** `character_baking_test.go` — `TestDeletedAccountKeepsItsMaskInPosts`
(пост показывает маску: имя, `is_character`, `character_id`, и при этом
`author_deleted`/`Deleted`), `TestFrozenMaskOfDeletedAccountCannotBeChanged`
(staff получает 403 на правку и удаление, строка маски не тронута).

## Проблема

При удалении пользователя (adb-действием админа) происходит хард-удалёние записи из коллекции `users`.  
Далее при открытии его профиля (`GET /api/aerun/users/{id}` → 404) страница профиля "срется":  
- посты пользователя остаются (хранят `author_id`), но ссылка на профиль ведёт в никуда  
- репутация, посты, кнопка ЛС, форма ответа — рендерятся на `undefined`  
- нельзя отличить "ещё загружается" от "пользователь удалён"

## Решение: Soft-delete с флагом

### 1. Бэкенд: флаг удалённости пользователя

В коллекцию `users` добавляется поле `is_deleted` (boolean, по умолчанию `false`).

**Удаление пользователя** (`adminDeleteUserHandler`) больше НЕ делает `txApp.Delete(targetUser)`.  
Вместо этого в одной транзакции:
- устанавливает `targetUser.Set("is_deleted", true)`
- устанавливает `targetUser.Set("status", "deleted")`
- **Очищает `targetUser.Set("nickname_normalized", "")`** — освобождает уникальность ника, чтобы новая регистрация под тем же ником была возможна (UNIQUE индекс частичный: `nickname_normalized != ''`)
- **Оставляет `nickname` как есть** — запеченный ник отображается на профиле удалённого пользователя
- пишет audit log `admin_user_delete`
- остальные данные (avatar_url, reputation, posts_count) **остаются** — они запекаются и показываются на профиле

### 2. GET /api/aerun/users/{id} (getUserProfileHandler)

- Если запись не найдена — 404 (как раньше).
- Если найдена и `is_deleted == true` — возвращает профиль **со статусом deleted** и флагом `deleted: true`, а не 404.  
  Поля: `id`, `nickname`, `role: "Deleted"`, `status: "deleted"`, `deleted: true`, `avatar`, `avatar_url`, `reputation`, `posts_count`, `created_at`, `settings` (суженые, как для чужого).
- Если найдена и `is_deleted == false` — как раньше.

### 3. GET /api/aerun/peers/{id} (getPeerCardHandler)

- Для deleted пользователя возвращает `nickname`, `avatar`/`avatar_url`, `status: "deleted"`, `deleted: true` — чтобы чат-шапка могла отобразить заглушку и понять, что писать нельзя.

### 4. POST /api/aerun/users/{id}/vote (voteUserHandler)

- Если цель `is_deleted == true` — `forbiddenError("cannot vote for a deleted user")`.  
  Новые голоса на профиль удалённого пользователя блокируются на сервере.

### 5. GET /api/aerun/nicknames/check (checkNicknameHandler)

- При проверке уникальности ника **игнорировать записи с `is_deleted == true`** (добавить условие `is_deleted != true` в запрос).  
  Это позволяет новому пользователю зарегистрироваться под ником, который носил удалённый аккаунт.

### 6. POST /api/aerun/dm/conversations (createDMHandler)

- Если любой из получателей `is_deleted == true` — отказ с 403/409. Новый диалог с удалённым пользователем создать нельзя.

### 7. POST /api/aerun/dm/conversations/{id}/messages (sendDMMessageHandler)

- Если собеседник в диалоге `is_deleted == true` — отказ. В existing диалог с удалённым писать нельзя.

### 8. Удаление диалога с удалённым

- Если один из участников диалога удалён (`is_deleted == true`), а второй удаляет диалог ("clear for me" / delete) — диалог удаляется из базы, так как живых читателей не остаётся.

### 9. Посты с масками удалённого пользователя

- Пост хранит `author_id` (основной аккаунт) и `author_character_id` (маска).  
- Если основной аккаунт `is_deleted == true`, отображаем имя/аватар **удалённого основного аккаунта** (не придумываем имя маски, не показываем маску как живого пользователя).  
- Роль автора в посте → `Deleted`.

### 9. loadAuthorDisplays / декорирование авторов

- Для deleted автора: `Nickname` = запеченный `nickname` из записи (как был при жизни аккаунта), `Role = "Deleted"`, `AvatarURL` = загруженный аватар пользователя (если был) или пусто, `Reputation` и `PostsCount` = запеченные значения из записи.

## 10. Фронтенд: страница профиля удалённого пользователя

`ProfilePage.jsx` получает `viewedProfile` из `subscribeToUser`.  
Когда `viewedProfile?.deleted === true`:

- Заголовок страницы / `<h2>` → запеченный ник + `(Удалён)` / `(Deleted)`.
- Аватар: если `viewedProfile.avatar_url` не пуст — показываем его; иначе — дефолтная аватарка (сторонний ресурс, dicebear/identity как для удалённого автора в постах).
- Инфоблок: только текст "Этот аккаунт удалён" / `This account has been deleted`. Статуса, роли, локации и прочего — нет.
- **Posts: N, Reputation: N** — запеченные значения из `viewedProfile.posts_count` / `viewedProfile.reputation` (как на целевом скриншоте).
- Все вкладки (posts, stats, characters, about, reputation, security) — **скрыты**.
- Кнопка ЛС (PM) / DirectMessages — **не рендерится**.
- Кнопки +/- репутации, голосование — **не рендерятся**.
- Кнопка редактирования профиля — **не рендерится**.
- `fetchUserPosts` — **не вызывается** (`if (isDeletedProfile) return`).

## 11. Фронтенд: посты удалённого пользователя

В темах/постах, где автор `is_deleted`:
- Ссылка на профиль автора — **скрыта** (никакой кликабельной ссылки на удалённый профиль).
- Кнопка ЛС (PM) у поста — **скрыта**.
- Роль автора — тег `Deleted`.
- Аватар: загруженный или дефолтный.
- Имя: запеченный `nickname` из записи (как был при жизни аккаунта).

## 12. Фронтенд: репутация и голоса

- Кнопки +/- репутации у постов/профиля удалённого пользователя — **скрыты** (сервер тоже блокирует, см. п.4).

## 13. Фронтенд: ЛС

- Открытые прежде диалоги с удалённым участником **сохраняются** (история читается).
- Кнопка "написать" / форма ответа в диалоге с удалённым — **скрыта**.
- Новый диалог с удалённым — нельзя создать (сервер блокирует, п.5).

## Границы ответственности

- Хард-удалёние постов/тем остаётся без изменений (посты удалённого пользователя остаются, если не выбран чекбокс удаления постов).
- Репутация, накопленная до удаления, остаётся запеченной (не откатывается автоматически).
- Сервер не откатывает голоса, уже отданные до удаления; блокирует только новые.
- Повторная регистрация под ником удалённого пользователя — разрешена (при удалении очищается `nickname_normalized`, и `checkNicknameHandler` игнорирует удалённые записи).

## Чекбокс «удалить все посты пользователя» при удалении аккаунта

### UI (AdminPage.jsx)

В диалоге подтверждения удаления пользователя добавляется чекбокс:
- `Удалить все посты этого пользователя` / `Delete all posts by this user`
- По умолчанию **отключён** (выбрано «удалить только аккаунт»).

### Контракт API

`DELETE /api/aerun/admin/users/{id}` принимает тело `{ delete_posts: boolean }` (или query-параметр `?delete_posts=1`).

### Бэкенд (adminDeleteUserHandler)

При получении флага `delete_posts == true`, в той же транзакции, что и soft-delete аккаунта:
1. Находит все `topics`, где `author_id == targetUserId` — удаляет их (хард-remove тем и всех постов в них).
2. Находит все `posts`, где `author_id == targetUserId` и не в удалённых темах — удаляет их.
3. Удаляет `reputation_votes`, где `voter_id == targetUserId` (голоса, отданные этим пользователем) и где `target_id == targetUserId && post_id == ''` (голоса в репутацию этого пользователя).
4. Пишет audit log `admin_user_delete` с пометкой `delete_posts: true`.
5. Soft-delete аккаунта: `is_deleted = true`, `status = 'deleted'`, `nickname_normalized = ''`.

При `delete_posts == false` (по умолчанию):
- Только soft-delete аккаунта (`is_deleted = true`, `status = 'deleted'`, `nickname_normalized = ''`).
- Посты остаются, автор помечается как `Deleted` с запеченным ником.

### Семантика

- «Удалить только аккаунт» — профиль становится страницей с запеченным ником и пометкой удалён, посты остаются.
- «Удалить все посты» — полное удаление контента пользователя (темы, посты, связанные голоса репутации) плюс soft-delete аккаунта.
