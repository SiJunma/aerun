# Спецификация: Архитектурный аудит и план рефакторинга модуля тем (Topic View)

> **Статус:** Анализ и Спецификация архитектурного рефакторинга  
> **Дата:** 28 октября 2026 г.  
> **Объект аудита:** `src/pages/TopicPage.jsx` (4 408 строк) и связанные модули (`src/api/forum.js`, хуки, модальные окна, утилиты)

---

## 1. Введение и цели аудита

Файл `TopicPage.jsx` является центральным и наиболее функционально нагруженным экраном форума. В ходе развития проекта он превратился в классический **God Component** («компонент-бог»):
- Объем: **4 408 строк** в одном файле.
- Внутреннее состояние: **более 40 переменных `useState`** и **более 30 `useRef`**.
- Эффекты: **более 15 независимых хуков `useEffect`**, многие из которых имеют перекрестные зависимости, вызывая каскадные ре-рендеры и гонки состояний.
- Дублирование верстки: разметка карточки поста продублирована 4 раза (десктопная версия поста, мобильная версия поста, закрепленный первый пост `pinnedFirstPost`, черновик `myDraft`).
- Смешение зон ответственности: в одном компоненте соединены сетевой транспорт (HTTP REST, SSE-сигналы, fallback-поллинг, мертвый RTDB-код), роутинг и синхронизация параметров URL (`?page=`, `?post=`, `?goLast=`, `#post-`), ручное управление DOM и скроллом через таймеры, оптимистичные мутации с ручным откатом, 6 модальных окон, клиентское кэширование авторов и масок, отслеживание непрочитанных цитат через `IntersectionObserver` и спасение неотправленных сообщений (`unsent-replies`).

### Ключевая проблема
Компонент страдает от хронических **гонок состояний (race conditions)** и **мерцаний интерфейса (UI flickers)**:
1. При входе в тему (особенно с флагами `goLast=1` или `?post=`).
2. При переключении страниц (полное стирание списка постов в белый экран).
3. При отправке нового сообщения (особенно когда ответ переносит пользователя на следующую страницу).
4. При получении внешних обновлений (когда другой пользователь отправляет пост или закрывает тему).
5. При удалении поста.
6. При редактировании сообщения.

Настоящий документ подробно фиксирует текущее устройство системы, все выявленные дефекты и гонки, а также предлагает бескомпромиссный план рефакторинга по лучшим практикам React (Clean Architecture, компонентное дробление, разделение логики на кастомные хуки, детерминированная модель данных).

## 2. Глубокий аудит текущего состояния (As-Is): Анатомия гонок состояний

### 2.1. Вход в тему (`goLast=1`, `?post=ID`, `#post-ID`)

#### Как это работает сейчас
При открытии страницы `TopicPage`:
1. Срабатывает `subscribeToTopicStats(id)`: запускается SSE/поллинг метаданных темы.
2. Тема изначально `null` — монтируется оверлей `TopicPageSkeleton`.
3. Когда приходят `stats`, вызывается `setTopic(stats)`.
4. Параллельно работают три эффекта:
   - Эффект контекста пользователя `fetchTopicContext(id)` (черновик, подписка, голоса репутации).
   - Эффект `loadPosts()` (строки 632–693).
   - Эффект контроллера навигации и скролла `Unified Navigation & Scroll Controller` (строки 1149–1375).

#### Где дыры и гонки состояний:
- **Двойной поиск поста (`Dual-locate race`):**  
  При переходе по ссылке на пост `?post=xyz`:
  - Функция `loadPosts` передает `targetPostId = queryPostId` в `fetchSecuredPosts(...)`. Бэкенд на Go уже умеет за один SQL-запрос через `COUNT` вычислить страницу и вернуть посты нужной страницы.
  - Однако параллельно срабатывает Scroll Controller (строка 1203), который *независимо* запускает `locatePost(queryPostId, ...)`, делая повторный сетевой запрос!
  - Оба запроса пытаются вызвать `setSearchParams({ page: resolvedPage })`. В React Router v7 `setSearchParams` генерирует новый `location.key` даже при `{ replace: true }`.
  - Это инвалидирует зависимости эффектов, приводит к повторному запуску `loadPosts` и сбросу `alreadyJumpedRef`.
- **Застревание в скелетоне из-за искусственного форсирования рендера:**  
  Чтобы заблокировать интерфейс на время прыжка к посту, используется `isJumping = needsJump && !alreadyJumpedRef.current`. Но поскольку `alreadyJumpedRef` — это `useRef`, его изменение не вызывает ре-рендер. Разработчикам пришлось добавить хак:
  ```javascript
  const [, forceJumpRender] = React.useReducer(x => x + 1, 0);
  const setAlreadyJumped = React.useCallback((value) => {
    if (alreadyJumpedRef.current === value) return;
    alreadyJumpedRef.current = value;
    forceJumpRender();
  }, []);
  ```
  Если сетевой запрос завершается ошибкой, или если элемент поста в DOM не успел отрендериться за 50 попыток по 100 мс (`tryScroll` таймер), флаг `alreadyJumped` может не переключиться или сброситься повторным эффектом `lastJumpIntentRef`, оставляя пользователя заблокированным серым оверлеем навсегда.
- **Гонка `readMapReady` при `goLast=1`:**  
  Если карта прочитанного `readMap` пользователя еще загружается из хранилища/сети, условие в строке 686:
  ```javascript
  if (user?.uid && !hasExplicitPage && !hasPostJump && !hasHashJump && searchParams.get('goLast') === '1' && !readMapReady) {
    setPosts([]);
    return;
  }
  ```
  очищает посты и ждет. Если `readMapReady` задерживается, а пользователь тем временем получает `topic`, происходит ложное срабатывание фолбэка по дате создания профиля (`profile.created_at`), из-за чего пользователя выбрасывает не на первое непрочитанное, а на случайную страницу, и тут же срабатывает `markTopicRead`, уничтожая маркеры непрочитанности для всей темы.

### 2.2. Листание темы (Пагинация)

#### Как это работает сейчас
При клике на номер страницы в `ForumPagination`:
1. Вызывается `handlePageChange(page)` -> `setSearchParams({ page })`.
2. Изменяется `currentPage`.
3. Срабатывает эффект загрузки постов (строки 632–693).

#### Где дыры и гонки состояний:
- **Мерцание белым экраном через `setPosts([])`:**  
  В начале эффекта при смене страницы жестко выполняется:
  ```javascript
  setPosts([]);
  loadPosts();
  ```
  Вместо того чтобы держать на экране текущую страницу (pattern Stale-While-Revalidate) с легким спиннером или полупрозрачностью, React мгновенно размонтирует все DOM-узлы постов. Весь блок контента схлопывается, экран прыгает вверх, показывается спиннер/скелетон, а после ответа сети посты рендерятся заново.
- **Гонка быстрых кликов (`Rapid pagination clicks`):**  
  Если пользователь быстро нажал «2», а затем «3»:
  - Запускаются два запроса к `fetchSecuredPosts`.
  - В коде есть `currentFetchId = ++activeFetchIdRef.current` — старый ответ действительно игнорируется.
  - Однако `currentPageRef.current` и `searchParams` могут разойтись с текущим контекстом рендера до того, как завершится последний промис, вызывая показ некорректного номера сообщения (`#index + indexOfFirstItem + 1`).
- **Гонка отметки о прочтении при перелистывании:**  
  Эффект отметки прочтения (строка 701) вычисляет:
  ```javascript
  const lastMessageIndex = (currentPage - 1) * ITEMS_PER_PAGE + posts.length - 1;
  ```
  В момент, когда `currentPage` уже изменился на 5, но посты страницы 5 еще не загрузились (или пришли частично), этот эффект может выполниться с промежуточными данными и передать на сервер некорректный оффсет, пометив прочитанными посты, которые пользователь даже не видел.

### 2.3. Отправка сообщения и работа с черновиком

#### Как это работает сейчас
В `submitReply` и `handlePublishDraft`:
1. Генерируется временный ID `tempId = temp_${Date.now()}_...`.
2. Просчитывается целевая страница:
   ```javascript
   const currentTotal = Math.max(topic?.posts_count || 0, (currentPage - 1) * ITEMS_PER_PAGE + posts.length);
   const newTotalPosts = currentTotal + 1;
   const targetPage = Math.ceil(newTotalPosts / ITEMS_PER_PAGE) || 1;
   ```
3. Если `targetPage === currentPage`, оптимистичный пост добавляется в массив `posts`.
4. Если `targetPage !== currentPage`, выполняется переход:
   ```javascript
   setSearchParams({ page: targetPage }, { preventScrollReset: true, state: { pendingPostId: tempId } });
   ```
5. Запускается сетевой запрос `createPost(...)` или `publishDraft(...)`.

#### Где дыры и гонки состояний:
- **Фатальная гонка межстраничной отправки («Пост исчезает»):**  
  Это один из самых частых багов, на который жалуются пользователи:
  - Пользователь на странице 1 (где уже 20 постов). Он пишет ответ. Новый пост должен стать 21-м (т.е. первой записью на странице 2).
  - Код вызывает `setSearchParams({ page: 2 })`.
  - Изменение URL немедленно активирует эффект загрузки постов страницы 2 (`loadPosts(2)`).
  - Эффект выполняет `setPosts([])` и делает запрос `fetchSecuredPosts` на сервер!
  - **Но запрос `createPost` еще находится в полете (in-flight) по сети!** Бэкенд еще не закоммитил транзакцию в базу данных!
  - Запрос `fetchSecuredPosts(page=2)` возвращает **0 постов** (пустую страницу).
  - `TopicPage` видит пустую страницу 2 и может автоматически откатить URL назад на страницу 1 или показать пустоту.
  - Оптимистичный пост исчезает.
  - Когда `createPost` наконец завершается, он пытается вызвать `navigateToCreatedPost`, но состояние уже потеряно. Пользователю кажется, что его сообщение пропало, пока он вручную не обновит страницу через F5!
- **Гонка публикации черновика с фоновым контекстом:**  
  В строках 93–97 объявлен флаг `draftJustPublishedRef = useRef(false)`. Он был добавлен как «костыль», потому что `setTopic`, вызванный при публикации черновика, повторно запускал эффект `fetchTopicContext`, который читал с сервера старый черновик (до того, как транзакция публикации завершилась) и снова восстанавливал карточку черновика на экране!
- **Разрушение формы при одновременной блокировке темы:**  
  Если во время набора текста тема закрывается или удаляется другим модератором, срабатывает эффект «спасения» `saveUnsentReply`, но из-за очистки формы в `setReplyContent('')` и несогласованности `savedReplyContent` в разных замыканиях текст может либо продублироваться в черновиках, либо затереться.

### 2.4. Обновления от других пользователей в реальном времени (Realtime)

#### Как это работает сейчас
В строках 252–331 присутствует 80 строк кода с подписками:
- `subscribeToNewPostsRtdb`
- `subscribeToPostRemovalsRtdb`

#### Где дыры и архитектурный обман:
- **Мертвый код RTDB:**  
  В файле `src/api/forum.js` (строки 390–396):
  ```javascript
  export const subscribeToNewPostsRtdb = (_topicId, _sinceTimestamp, _callback) => {
    return () => {};
  };
  export const subscribeToPostRemovalsRtdb = (_topicId, _callback) => {
    return () => {};
  };
  ```
  Эти функции — **пустые заглушки**! Они ничего не делают после миграции с Firebase на Go/SQLite. 80 строк кода в `TopicPage` с обработкой добавления авторов, подсветкой и фильтрацией — чистый балласт.
- **Шторм повторных запросов и стирание экрана при внешнем посте:**  
  Как на самом деле приходят обновления? Через `subscribeToTopicStats` (SSE сигнал `topic.post` или 15-секундный опрос):
  1. Приходит новый `posts_count` и новый `last_post_id`.
  2. Вызывается `setTopic(newStats)`.
  3. **Срабатывает Эффект 1 (строки 606–629):**
     Видит `newLastPostId !== prevLastPostId` -> вызывает `loadPosts(currentPage)`.
  4. **Срабатывает Эффект 2 (строки 632–693):**
     Зависит от `topic`. Проверяет `currentTopicKey = ${id}|${topic.last_post_id}`. Ключ изменился!
     Вызывает `setPosts([])` (стирает все посты с экрана!) и **тоже** вызывает `loadPosts()`.
  5. **Итог:** Два параллельных сетевых запроса за одними и теми же данными. Экран пользователя мерцает и гаснет, даже если он спокойно читал страницу 2, а кто-то оставил комментарий на странице 10! Чтение пользователя грубо прерывается.

### 2.5. Удаление поста

#### Где дыры и гонки состояний:
- **Воскрешение удаленного сообщения (Ghost Post Resurrection):**  
  При удалении поста вызывается `setPosts(prev => prev.filter(p => p.id !== targetPostId))`, и параллельно отправляется `deletePost(...)`.  
  Если в этот интервал (обычно 100–300 мс) срабатывает фоновый опрос `subscribeToTopicStats`, бэкенд возвращает еще старый `posts_count` или кэшированный `last_post_id`. В результате срабатывают Эффекты 1 и 2, запускается `loadPosts()`, и удаленный пост **снова появляется на экране на несколько секунд**, пока следующий опрос его не скроет.
- **Удаление единственного поста на странице:**  
  Если на странице 3 был только один пост, и пользователь его удаляет, локальный массив `posts` становится пустым `[]`. Логика перенаправления на страницу `currentPage - 1` размазана между обработчиком клика и эффектами `loadPosts`, из-за чего интерфейс на время зависает в состоянии ошибки или пустого экрана.
- **Удаление первого поста:**  
  Удаление первого поста темы семантически удаляет всю тему. Если бэкенд возвращает `409 Conflict` (например, автор не имеет права удалять тему, если в ней уже есть ответы других игроков), локальный пост уже оптимистично скрыт, и требуется принудительный откат, который сейчас реализован через повторный полный перезапрос темы.

### 2.6. Редактирование поста

#### Где дыры и гонки состояний:
- **Блокирующий `window.alert` в коде:**  
  В строке 2471 при ошибке редактирования вызывается:
  ```javascript
  alert('Error editing post');
  await loadPosts();
  ```
  Это грубейшее нарушение современных стандартов React и правил проекта о прозрачной диагностике без блокировки браузерного потока.
- **Гонка при редактировании первого сообщения темы:**  
  При сохранении первого поста вызывается `updatePost`, а затем `updateTopic` (для заголовка/описания/закрепления). Вызов `setTopic` провоцирует лавину эффектов 1 и 2, из-за чего посты снова могут быть стерты через `setPosts([])` прямо во время закрытия формы редактирования.
- **Потеря бросков кубиков при редактировании:**  
  Если отредактировать сообщение с дайсами, логика слияния `existingRolls` и `freshRolls` должна строго гарантировать, что старые сгенерированные результаты бросков `[roll=id]` не затираются, пока пользователь не удалил сам тег из текста.

### 2.7. Каскады гидратации авторов и масок (N+1 Client Fetching)

В `TopicPage.jsx` встроены каскадные эффекты гидратации:
- Строки 989–1026: обход постов, сбор неизвестных ID персонажей (`author_character_id`), массив `Promise.all(pending.map(fetchCharacter))`, запись в `setMaskStats`.
- Строки 1033–1091: обход постов, сбор неизвестных UID пользователей без подписей, цикл `missingUids.forEach(fetchUserProfile)`, запись в `setAuthorStats`.

**Проблема:**  
Каждый ответ обновляет состояние `maskStats` или `authorStats`, что вызывает повторный рендер всего огромного дерева `TopicPage` (всех 20 постов). А если зависимости эффекта составлены неидеально, обновленный `maskStats` провоцирует повторный запуск эффекта на следующем тике, вызывая лавину микрозапросов и предупреждений в консоли.

## 3. Целевая архитектура (To-Be): Чистый компонентный дизайн

Рефакторинг `TopicPage` должен следовать ключевым принципам:
1. **Single Responsibility Principle (SRP):** Страница — это лишь верхнеуровневый координатор. Каждая визуальная и функциональная часть выносится в отдельный изолированный компонент.
2. **Никакого полного стирания экрана (`No setPosts([])`):** Использование паттерна фонового обновления (Stale-While-Revalidate). Предыдущая страница остается интерактивной, пока загружается следующая.
3. **Изоляция модальных окон:** Модалки не должны перегружать состояние страницы.
4. **Кастомные хуки для логики (Separation of Concerns):** Вся работа с данными, мутациями, скроллом и черновиками уходит в специализированные хуки.
5. **Соответствие DOM-спецификации тем:** Использование стабильных классов и идентификаторов в соответствии с `SPEC_forum-topic-view-theme-dom.md`.

### 3.2. Слой логики: Специализированные хуки

## 4. Спецификация ключевых модулей

### 4.1. Управление состоянием постов: `useTopicPosts`

**Главная задача:** Избавиться от мерцаний, двойных запросов и гонок пагинации.

```javascript
/**
 * Контракт хука useTopicPosts
 */
export const useTopicPosts = (topicId, targetPage, pageSize) => {
  // Состояние:
  // - posts: текущие отображаемые посты
  // - isFetching: идет ли фоновый запрос новой страницы
  // - error: ошибка загрузки
  // - totalPosts: актуальное общее количество постов
  // - totalPages: количество страниц
  // - optimisticPosts: очередь локально созданных постов
  
  // Методы:
  // - addOptimisticPost(post)
  // - updateOptimisticPost(tempId, realPost)
  // - removeOptimisticPost(tempId)
  // - removePostLocally(postId)
  // - updatePostLocally(postId, updatedFields)
  // - reloadCurrentPage()
};
```

#### Принципы устранения гонок:
1. **Никакого `setPosts([])` при смене страницы:** При переходе со страницы 1 на страницу 2 `posts` сохраняет посты страницы 1, пока запрос страницы 2 находится в полете. Выставляется флаг `isFetching = true`, на список накладывается аккуратный индикатор загрузки. Пользователь видит стабильный интерфейс.
2. **AbortController на каждый запрос:** При быстрой смене страниц предыдущий запрос немедленно отменяется через `abortController.abort()`.
3. **Интеллектуальная реакция на фоновый `topic.post`:**  
   Когда от другого пользователя приходит сигнал о новом посте:
   - Если текущий пользователь находится **НЕ на последней странице** темы: посты текущей страницы **НЕ перезагружаются**! Обновляется только `totalPosts` и счетчик страниц в пагинации. Чтение пользователя не прерывается.
   - Если пользователь находится **на последней странице**: новый пост плавно добавляется в конец списка (или выводится ненавязчивая плашка «Появились новые ответы v»).

---

### 4.2. Межстраничная отправка и оптимистичный пайплайн: `useTopicMutations`

**Главная задача:** Гарантировать, что при отправке сообщения на границе страницы (переход на страницу N+1) пост никогда не теряется из виду.

#### Алгоритм решения:
1. Пользователь нажимает «Отправить».
2. Генерируется оптимистичный пост с временным идентификатором `tempId`.
3. Вычисляется целевая страница: `targetPage = Math.ceil((totalPosts + 1) / pageSize)`.
4. **Если `targetPage !== currentPage`:**
   - Хук мутаций сохраняет оптимистичный пост в глобальную очередь ожидания темы (`pendingOptimisticQueue`).
   - Инициируется переход `navigate('/topic/${topicId}?page=${targetPage}')`.
   - Хук `useTopicPosts` на новой странице монтирует список, содержащий этот `pendingOptimisticPost`, даже если бэкенд еще не успел вернуть ответ на `createPost`!
   - Когда `createPost` возвращает постоянный `postId`, временный пост замещается реальным без перезагрузки всей страницы.
5. Скролл плавно фокусируется на элементе `#post-${tempId}` -> затем плавно переключается на постоянный ID.

### 4.3. Универсальная карточка поста: `TopicPostCard`

**Главная задача:** Устранить чудовищное дублирование верстки (сейчас десктоп и мобилка написаны двумя отдельными блоками кода внутри одного файла).

#### Архитектурное решение:
- Один компонент `TopicPostCard.jsx`, принимающий пропсы:
  - `post`: объект сообщения.
  - `postNumber`: порядковый номер в теме.
  - `isPinnedFirstPost`: флаг первого закрепленного поста.
  - `isDraft`: флаг карточки черновика.
  - `isEditing`: находится ли данный пост в режиме редактирования.
  - `onQuote`, `onEdit`, `onDelete`, `onVote`, `onSaveEdit`, `onCancelEdit`.
- Адаптивность реализуется через CSS-классы (`.post-author`, `.post-body`, медиа-запросы в CSS), а не через дублирование веток JSX (`d-none d-md-flex` vs `d-md-none`).
- Все селекторы и структура DOM строго соответствуют `SPEC_forum-topic-view-theme-dom.md`:
  - Корневой узел: `<article id="post-${post.id}" class="post ${isOnline ? 'online' : ''} ...">`
  - Автор: `<div class="post-author">`
  - Контент: `<div class="post-content">`
  - Подпись: `<div class="post-signature">`
  - Действия: `<div class="post-actions">`

Все 6 модальных окон выносятся из тела страницы в изолированный контейнер `TopicModalsContainer`:
- `ConfirmModal` (удаление поста).
- `ConfirmModal` (удаление темы).

### Этап 6: Исправление оптимистичного Author DTO (Mask / Role / Scroll) — ВЫПОЛНЕНО ✅

**Проблема:** `ForumAuthorAvatar` и `ForumAuthorName` читают вложенный объект `post.author` (поля `avatar_url`, `display_name`, `user_id`, `character_id`), а `getRoleBadge` определяет роль по `post.author?.user_id`. Все три мутации (`submitReply`, `handlePublishDraft`, `handleSaveEdit`) обновляли только **плоские** поля (`post.author_name`, `post.author_avatar`…), не трогая вложенный `post.author` — в результате:
1. Смена маски при редактировании поста не отображала новую аватарку/имя до перезагрузки страницы.
2. Опубликованный черновик рендерился с бэйджем «Гость», т.к. `post.author?.user_id` был `undefined`.
3. Новый пост через форму ответа тоже мог показывать «Гость» (если `ownNewStats` был `null`).
4. После сохранения редактирования пост не скроллился в область видимости.
5. При сохранении черновика под маской `users.last_selected_character_id` сохранялся в профиле. При попытке отредактировать черновик и вернуть его на основной аккаунт (`character_id: ""`), бэкенд `upsertDraftHandler` через `resolveAuthorCharacter` ошибочно подтягивал сохраненную в профиле маску вместо сброса на основной аккаунт. Из-за этого черновик не возвращался на аккаунт и сбрасывался на первую маску.

**Решение:**
- [x] Добавлен хелпер `buildAuthorDTO(charId)` — строит консистентный вложенный `author` объект (kind, user_id, display_name, avatar_url, character_id, role_id) из текущего `profile`, `user`, `characters`.
- [x] `submitReply`: оптимистичный пост **всегда** включает `author: { ...buildAuthorDTO(...) }`, не зависимо от `ownNewStats`.
- [x] `handlePublishDraft`: оптимистичный пост включает `author` DTO. При получении ответа сервера — `convergedAuthorDTO` из серверного `pubResult.author` + фолбэки.
- [x] `handleSaveEdit`: при изменении маски (`metadata` не пуст) — `setPosts` также обновляет `post.author` через `buildAuthorDTO(editCharacterId)`.
- [x] `handleSaveEdit`: добавлен `scrollIntoView({ behavior: 'smooth', block: 'center' })` + подсветка `highlight-new-post` после сброса формы редактирования.
- [x] `backend/internal/platform/pocketbase/drafts.go`: в `upsertDraftHandler` пустой `character_id` (`""`) теперь гарантированно сбрасывает `author_character_id: ""` и не фолбэчится на `last_selected_character_id` профиля.
- [x] `backend/internal/platform/pocketbase/drafts_test.go`: добавлен тест `TestDraftClearingMaskDoesNotFallbackToProfileMask` (проверяет сохранение под маской 1 -> сброс на аккаунт -> смена на маску 2 -> повторный сброс на аккаунт).
- [x] `src/pages/TopicPage.jsx`: `decorateDraft` теперь корректно обрабатывает переданный `charId = ''` как явный выбор основного аккаунта, `handleUpdateDraft` выполняет плавный скролл к обновленному черновику с подсветкой, а кнопки «Отмена» очищают `editCharacterId`.
