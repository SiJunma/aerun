# CONCEPT: Кастомные поля профиля

Статус: концепт.

## 0. Что это и зачем

Аналог настройки «поля профиля» из MyBB / RusFF: администратор в админке создаёт
произвольное текстовое мета-поле, привязанное к профилю пользователя. Поле может
быть запрещено редактировать или запрещено видеть (вплоть до «не видит даже сам
владелец») — на основе роли. Отдельно выбирается, показывать ли поле в профиле
и в карточке автора в постах.

Зачем: поле — это просто значение. Типичные использования:

- текст (ник в Discord, любимый персонаж, город);
- ссылка (профиль в соцсети, картинка-аватарка, баннер);
- сырой код/значение (цвет, класс иконки, строчка HTML-кода), которое потом
  кастомный JS/CSS темы подхватывает и оформляет как надо.

Ключевая идея концепта: **поле хранит сырой текст, а вид ему придаёт тема**.
Сам форум в v1 умеет пять типов отображения (см. §7), пятый — `html` — только
через санитайзер (§7.1), а всё остальное — через CSS-класс поля и кастомный JS темы.

## 1. Ключевые решения

| Вопрос | Решение | Почему так |
|---|---|---|
| Где хранить определения и значения | Две новые коллекции PocketBase: `profile_field_definitions` и `profile_field_values` (§2) | Как в MyBB: определение отдельно от значений. Не `users.settings`: это приватный JSON-блоб владельца на 256 КБ, а его публичная часть — whitelist ровно из трёх ключей (`signature`, `rep_show_history`, `rep_show_comments`, `user_profile.go`). Расширять его под чужие роли и видимость — значит ломать уже принятое разделение |
| Стабильный id поля | Человекочитаемый `key` (`^[a-z0-9_]{1,64}$`, уникален, неизменяем после создания) + CSS-класс `pf-<key>` и атрибут `data-profile-field="<key>"` | PocketBase-`id` записи тоже стабилен, но нечитаем. `key` — это то, на что опираются темы, JS и документация. Переименование подписи (`label`) ключ не меняет |
| Что такое «значение» | По умолчанию plain text; тип `html` — сырая разметка, но только через allowlist-санитайзер (§7.1) | Значение — ввод пользователя. Сырой HTML без санитайзера — это XSS-вектор, поэтому тип `html` рендерится только после `sanitizeHtml`, а не как есть |
| Кто решает, что видно | Только сервер (§4). UI лишь не рисует то, чего нет в ответе | Жёсткое правило проекта: доступ решается на сервере, никогда только в UI |
| Поля — аккаунту или маске? | Только аккаунту (`users`). Пост под маской показывает поля человека-владельца | Как счётчики: репутация и число постов в `TopicPostCard` — человеческие, а не маски (`forum_authors.go`: «the reputation counters stay the human's»). Маска — display-identity, не владелец |
| Кэшировать ли значения в постах? | Нет. Значения резолвятся при чтении, как ник и аватар | Посты хранят только `author_id` (`forum_authors.go`). Кэш в постах — это дрифт, из-за которого переименованный участник keeps old nickname на тысяче постов. Поменял значение — оно обновилось везде сразу |
| Права на управление | Новое право `manage_profile_fields` (§3), по образцу `mention_all` | Управление определениями — админская операция, ей нужен свой ключ, а не `manage_forum` целиком |

## 2. Модель данных

### 2.1. `profile_field_definitions` — одно поле = одна строка

| Поле | Тип | Комментарий |
|---|---|---|
| `key` | text, required, unique | Стабильный slug, см. §1. После создания не редактируется |
| `label` | JSON `{en, ru}` | Подпись, как `forumName` (`{en, ru}`) в `forum_settings`. Фронтенд берёт язык читателя, fallback — `en` |
| `type` | select: `text` / `textarea` / `url` / `image_url` / `html` | Тип отображения (§7). `html` — сырая разметка через санитайзер (§7.1) |
| `max_length` | number | Дефолты: `text` 256, `textarea` 4096 (как `bio`), `url`/`image_url` 512, `html` 4096. Жёсткий потолок — дефолт типа (для `html` — 16384), админ может только уменьшать |
| `placeholder` | text, optional | Подсказка в форме редактирования (тоже `{en, ru}`? — в v1 одна строка, см. §11) |
| `sort_order` | number | Порядок в профиле и в карточке автора |
| `is_active` | bool, default `true` | Неактивное поле нигде не показывается и не редактируется, значения сохраняются |
| `show_in_profile` | bool, default `true` | Показывать в профиле (вкладка «О себе») |
| `show_in_posts` | bool, default `false` | Показывать в карточке автора в теме. Дефолт `false`: пост — тесное место, поле туда попадает осознанно |
| `visibility` | select: `all` / `members` / `roles` | Кто видит значение (§3). Дефолт — `all` |
| `visible_roles` | select multi, role ids | Только при `visibility = roles`. Пустой список = не видит никто, кроме админ-контекста (§3) |
| `owner_can_edit` | bool, default `true` | Может ли владелец сам заполнять поле |

Правила коллекции — все `nil` (List/View/Create/Update/Delete), как у `roles`:
браузер в коллекции напрямую не пишет, всё — через команды `/api/aerun/*`.
Индекс: уникальный по `key`. Лимит: не более 50 активных определений
(защита от разрастания профиля и полезной нагрузки страницы темы).

### 2.2. `profile_field_values` — одно значение = одна строка

| Поле | Тип | Комментарий |
|---|---|---|
| `user_id` | relation → `users`, required | Владелец значения |
| `field_id` | relation → `profile_field_definitions`, required | Определение |
| `value` | text, required | Сырой текст. Пустая строка не хранится: очистка = удаление строки |

Правила коллекции — все `nil`, как у определений. Индекс: уникальный
`(user_id, field_id)`. Каскада при удалении пользователя нет отдельного:
удаление аккаунта в проекте — hard/soft по своим правилам, значения уходят
вместе с аккаунтом тем же механизмом, что и остальные его строки.

### 2.3. Почему не JSON на `users`

- `users.settings` — приватный блоб владельца; его публичная часть — whitelist
  из трёх ключей, и каждый новый ключ там — отдельное решение о приватности.
- По JSON нельзя сделать индекс «все значения поля X», нельзя посчитать
  «сколько пользователей заполнили поле», нельзя применить per-field видимость
  без разбора блоба на каждый запрос.
- Отдельная коллекция значений — это ровно тот запрос, который нужен странице
  темы: «значения полей Y для авторов Z» одним запросом (§5).

## 3. Права и видимость

### 3.1. Новые и переиспользуемые ключи

- **Новое: `manage_profile_fields`** — создавать/редактировать/деактивировать
  определения, видеть все значения в админ-контексте. Добавляется в
  `backend/internal/auth/permission.go` (`PermManageProfileFields`),
  в `frontend/src/constants/permissions.js` (`MANAGE_PROFILE_FIELDS`) и в
  матрицу системных ролей (по умолчанию — chief admin / root).
  Миграция — по образцу `1769500000_mention_all_permission.go`:
  расширить словарь `roles.permissions` (`repairRolePermissionDictionary`)
  и сверить системные роли (`reconcileSystemRolePermissions`). Кастомные роли
  не трогаются.
- **Переиспользуется: `edit_others_profile`** — редактировать чужие значения.
  Это тот же ключ, что покрывает биографический блок (bio, location, birthday,
  occupation, interests, contacts — `permission.go`, комментарий к
  `PermEditSelfProfile` / `PermEditOthersProfile`). Кастомные поля живут
  в той же панели «О себе», поэтому чужие значения редактируются тем же ключом.
  По умолчанию он админский, модераторам не выдаётся — и это осознанно:
  это личные факты, а не контент.
- Своего ключа `edit_self_profile_fields` не нужно: своё значение правит
  владелец, если `owner_can_edit = true` (§3.3).

### 3.2. Видимость: кто видит значение

Видимость считается **на сервере, для каждого читателя отдельно**, и владелец
исключением не является — это и есть запрошенное «запретить видеть у себя
в профиле» (например, служебная пометка, которую заполняет администрация,
а пользователь видеть не должен).

| `visibility` | Видят |
|---|---|
| `all` | Все, включая гостей |
| `members` | Только авторизованные |
| `roles` | Только те, чья эффективная роль в `visible_roles` |

Эффективная роль — та же, что использует остальной код: `custom_role_id`,
если задан, иначе `users.role` (при реализации свериться с резолвером ролей
в `admin_users.go` / `internal/auth` — в разных местах проекта роль резолвится
одинаково, и здесь изобретать свой резолвер нельзя).

Административный контекст — исключение: держатель `manage_profile_fields`
в админке (вкладка полей, карточка пользователя) видит все значения,
включая скрытые для его же роли, с пометкой «скрыто для роли X».
На публичных поверхностях (профиль, посты) исключений нет: админ там —
такой же читатель, как все.

Удалённый аккаунт: кастомные поля не показываются вообще (как и био-блок:
профиль удалённого — это baked-счётчики и плашка «Deleted», а не личные факты).
Забаненный аккаунт: поля показываются по обычным правилам видимости —
бан ограничивает действия, а не видимость (`user_profile.go`).

### 3.3. Редактирование: кто правит значение

| Кто | Условие |
|---|---|
| Владелец | `owner_can_edit = true` **и** владелец видит поле по §3.2 (нельзя править вслепую то, чего не видишь) |
| Сотрудник | Держит `edit_others_profile`, правит в админ-контексте (видит все значения) |
| Никто другой | — |

Правки сотрудником чужого значения пишутся в `audit_logs` (как переименование:
аудит с old/new value). Свои правки не аудируются — как правки био.

## 4. API (бэкенд, Go / PocketBase)

Всё — команды `/api/aerun/*`, браузер в коллекции не пишет. Мутации —
с `Idempotency-Key`, тело ограничено (как `profileBodyBytes = 32 KiB`
в `profile_commands.go`), ошибки — единый контракт
`data.{retryable, conflict, forbidden, validation, kind, request_id}`.

### 4.1. Новые команды

| Команда | Кто | Что делает |
|---|---|---|
| `GET /api/aerun/admin/profile-fields` | `manage_profile_fields` | Список определений (все, включая неактивные) + счётчик заполненных значений на каждое |
| `POST /api/aerun/admin/profile-fields` | `manage_profile_fields` | Создать определение. `key` проверяется на формат и уникальность |
| `PATCH /api/aerun/admin/profile-fields/{id}` | `manage_profile_fields` | Редактировать определение. `key` менять нельзя; `label`, `type`, лимиты, флаги — можно. Смена `type` не переписывает существующие значения, но при следующем сохранении они валидируются по новому типу |
| `DELETE /api/aerun/admin/profile-fields/{id}` | `manage_profile_fields` | Удалить определение **только если значений нет**. Если значения есть — 409, админ сначала деактивирует (`is_active = false`). Значения при деактивации не удаляются |
| `PATCH /api/aerun/me/profile-fields` | авторизованный | Свои значения: `{ "values": { "<key>": "<value>", ... } }`. Неизвестный ключ — 400 `validation` (allowlist, как `profileFieldNames` в `profile_commands.go`). Пустая строка — очистить значение (удалить строку) |
| `PATCH /api/aerun/users/{id}/profile-fields` | `edit_others_profile` | Чужие значения, тот же формат. Пишется в `audit_logs` |

Валидация значений — на сервере, по типу: `url` / `image_url` — парсинг URL,
только `http(s)` (никаких `javascript:`); длина — не больше `max_length`
определения; тип `text` — одна строка (переводы строк отбрасываются).

### 4.2. Изменение существующих хендлеров

- **`GET /api/aerun/users/{id}`** (`getUserProfileHandler`, `user_profile.go`):
  в payload добавляется `custom_fields: [{key, label, type, value}]` — только
  определения с `show_in_profile = true` и `is_active`, только те, что видны
  этому читателю (§3.2), в порядке `sort_order`. Гость получает поля
  с `visibility = all` — и это осознанно: в отличие от био (только для
  залогиненных, `addLoggedIn`), у кастомного поля своя видимость, и `all`
  означает именно «включая гостей».
- **`loadAuthorDisplays`** (`forum_authors.go`): `authorDisplay` расширяется
  полями с `show_in_posts = true` — **одним дополнительным запросом на всех
  авторов страницы**, а не запросом на автора (правило файла: «ONE query per
  page, not one per row»). Фильтр видимости — тот же, что в §3.2, для читателя
  страницы. Неизвестный автор — как сейчас: декорация просто не добавляется.
- **`GET /api/aerun/users`** (список участников): кастомные поля НЕ добавляются.
  Это список, а не профиль; при необходимости — отдельный флаг в v2.
- **`PATCH /api/aerun/me/profile`** и **`PATCH /api/aerun/users/{id}/profile`**
  (`profile_commands.go`) не меняются: кастомные значения — не колонки `users`,
  поэтому через `applyProfile` / `profileFieldNames` они не проходят.
  Отдельные команды из §4.1 — это и есть их путь сохранения.

## 5. Фронтенд: профиль

`frontend/src/pages/ProfilePage.jsx`:

- **Вкладка «О себе»** (`eventKey="about"`, рядом с био-блоком ~строка 973):
  после bio/location/birthday/occupation/interests/contacts — блок кастомных
  полей. Каждое поле: подпись (`label` на языке читателя) + значение по типу
  (§7). Пустые поля не рисуются. Порядок — `sort_order`.
- **Вкладка «Профиль»** (`eventKey="account"`, форма `handleSaveProfileTab`,
  `PROFILE_TAB_KEYS`): поля, которые читатель может редактировать (§3.3),
  добавляются в ту же форму, рядом с био-полями. Поле, которое владелец
  видеть не должен, в форме не появляется вообще (сервер его не прислал).
  Поле, которое владелец видит, но не может править (`owner_can_edit = false`),
  показывается в «О себе», но в форме отсутствует. Сохранение — отдельной
  командой из §4.1, а не вместе с био: у значений свой allowlist и своя
  валидация, смешивать их в один запрос — значит смешивать две сущности.
- Сотрудник, открывший чужой профиль, видит в форме поля, которые может править,
  с пометкой «видно только администрации» там, где `visibility` уже, чем `all`.

## 6. Фронтенд: посты

`frontend/src/components/topic/TopicPostCard.jsx`, блок `<dl className="post-author__meta">`
(сейчас там две строки: посты и репутация):

```jsx
<div className="post-author__meta-row post-author__meta-row--custom-field pf-discord"
     data-profile-field="discord">
  <dt className="post-author__meta-label">Discord:</dt>
  <dd>username</dd>
</div>
```

- Строки идут после репутации, в порядке `sort_order`. Рядятся только поля
  с `show_in_posts = true`, которые видны читателю.
- Один DOM для десктопа и мобильного (правило `SPEC_forum-topic-view-theme-dom.md`):
  та же `<dl>`, CSS решает, как она выглядит на узком экране. Мобильный
  icon-only ряд (`post-author__stats-mobile`, только посты/репутация) не
  расширяется — кастомные поля там не поместятся и не нужны.
- Источник данных — тот же батч, что и `authorStats` для страницы
  (`useTopicPosts.js` / `fetchSecuredPosts`): значения приезжают вместе
  со статистикой авторов, отдельным запросом на страницу, а не на пост.
- Классы и атрибуты — это контракт для тем (§7): `pf-<key>` и
  `data-profile-field="<key>"` стабильны, пока жив `key` определения.

## 7. Рендер по типам и контракт для кастомных тем

| Тип | Рендер по умолчанию (без кастомного JS) | Контракт для темы |
|---|---|---|
| `text` | Экранированный текст (React по умолчанию экранирует) | `.pf-<key> dd` — текст как есть |
| `textarea` | Экранированный текст с сохранением переносов (`white-space: pre-line`) | То же |
| `url` | `<a href target="_blank" rel="noreferrer">`, текст ссылки — само значение, обрезанное CSS | `a[href]` внутри `.pf-<key>` |
| `image_url` | `<img loading="lazy" alt="<label>">`, размер ограничен CSS темы | `img` внутри `.pf-<key>` |
| `html` | Разметка после `sanitizeHtml` (§7.1), рендер через `dangerouslySetInnerHTML` только с очищенной строкой | DOM внутри `.pf-<key>`, теги только из allowlist |

- **Для всех типов, кроме `html`, — никакого `dangerouslySetInnerHTML`.**
  Значение — это текст в DOM (`textContent`), и кастомный JS темы может его
  прочитать и перестроить (например, поле с кодом цвета красит бейдж, поле
  с классом иконки ставит иконку).

### 7.1. Тип `html`: что разрешено, а что вырезается

Хорошая новость: изобретать санитайзер не надо — он в проекте уже есть, и
даже два, с одинаковым allowlist (комментарий в `utils/text.js` прямо говорит,
что списки намеренно дублируются, чтобы поверхности не расходились):

- `sanitizeHtml` в `frontend/src/utils/text.js` — возвращает очищенную строку
  для `dangerouslySetInnerHTML`; им уже чистятся баннер-объявление и
  maintenance-сообщение (`Layout.jsx`, `LoginPage.jsx`);
- `safeHtmlToReact` в `frontend/src/components/common/BBCode.jsx` (SEC-02) —
  тот же allowlist, но возвращает React-дерево для `[html]` в постах.

Тип `html` использует `sanitizeHtml` — и именно его, а не новый третий список.
Три поверхности — один ответ на вопрос «что такое безопасная разметка».

**Разрешены** (уже есть в allowlist): `div`, `span`, `p`, `br`, `hr`,
`b`, `strong`, `i`, `em`, `u`, `s`, `del`, `strike`, `small`, `sub`, `sup`,
`a`, `img`, `table`/`thead`/`tbody`/`tr`/`td`/`th`, `ul`, `ol`, `li`,
`dl`/`dt`/`dd`, `h1`–`h6`, `blockquote`, `pre`, `code`, `q`, `cite`,
`section`, `article`, `header`, `footer`, `main`, `figure`, `figcaption`.

**Новое в allowlist** (добавляется в оба списка одновременно, иначе поверхности
разойдутся): `audio`, `video`, `source`. Плеер, который ты видела на другом
форуме, — это `<audio controls src="...">`; `source` нужен внутри
`audio`/`video`, чтобы дать несколько форматов файла. `video` — родной брат
аудио, тот же класс риска, поэтому добавляется вместе с ним, а не отдельно.

**Разрешённые атрибуты:** `class`, `id`, `href`, `src`, `alt`, `title`,
`width`, `height`, `type` (уже есть) плюс для медиа: `controls`, `preload`,
`loop`, `muted`, `poster`. И только классы: атрибут `style` для значений полей
**запрещён** (в отличие от баннеров, где он есть в отфильтрованном виде) —
вид задаёт CSS темы через `pf-<key>`, а не инлайн-стили.

**Запрещено всегда, без исключений:** `script`, `style` (тег), `iframe`,
`object`, `embed`, `form`, `input`, `button`, `select`, `textarea`, `svg`,
`meta`, `link`, `base`, все `on*`-обработчики, `javascript:` / `vbscript:` /
`data:text/html` / `blob:` / `file:` в `href`/`src`. Неизвестный тег удаляется
вместе со всем поддеревом (дети не «вытаскиваются» наружу). При ошибке парсера
рендерится пустота, а не исходник — санитайзер, который при сбое отдаёт вход,
это дыра, а не санитайзер (так уже сделано в `sanitizeHtml`).

**Медиа-правила:**

- `autoplay` запрещён: страница темы с десятью плеерами не должна начать
  играть сама. `preload="none"` — дефолт для аудио/видео в постах, чтобы
  страница не тянула все файлы сразу.
- URL — только `http(s)` и относительные пути; `data:` — только
  `data:image/*` для картинок. Аудио/видео по `data:` не пройдёт: файл должен
  лежать по обычному URL, загрузок файлов в v1 нет.
- Внешняя картинка/аудио — тот же риск, что у `avatar_url`: чужой сервер видит
  IP запросившего. Для форума это уже принятый риск, отдельно не оговаривается.

**Доверенного тира здесь нет.** В `[html]`-постах он есть: автор с ролью
`root`/`admin` может `script`/`style`/`iframe` (`BBCode.jsx`,
`isTrustedAdminRole`, SEC-02). Для значений полей тир не действует: значение —
ввод любого участника, строгий allowlist один для всех, включая админов.
Если админу нужен скрипт или вставка со сторонней страницы — это не значение
поля, а баннер/пост, и делается существующими механизмами.

**Санитизация — при рендере, а не при записи** (как `[html]` в постах: сервер
хранит сырой текст, чистит рендер). Сервер на записи проверяет только длину
и тип — Go-санитайзера в проекте нет (`bluemonday` в `go.mod` отсутствует),
а вводить его ради одного поля — лишняя зависимость. Следствие-инвариант:
html-значение нигде не рендерится без `sanitizeHtml` — ни в профиле, ни
в постах, ни в будущих поверхностях.
- Цвета — только через CSS-переменные темы, без инлайн-стилей (правило
  `TopicPostCard`: no inline styles, no utility classes).
- Все строки — через `t()` и `src/i18n/dictionary.js` (`admin.profile_fields.*`,
  `profile.custom_fields.*`). Хардкод-строк в UI нет (правило проекта).

## 8. Админка

`frontend/src/pages/AdminPage.jsx`: новая вкладка `profile_fields`
(после `roles`, до `categories`), в `canAccessTab` — по `manage_profile_fields`.
Вкладка содержит:

- таблицу определений: `key`, подпись, тип, `show_in_profile` / `show_in_posts`,
  видимость, `owner_can_edit`, активность, число заполненных значений;
- форму создания/редактирования: все поля из §2.1, `key` — только при создании;
- деактивацию вместо удаления, пока есть значения (§4.1);
- подсказку с примером: какое значение в поле ожидается и какой класс
  (`pf-<key>`) оно получит — чтобы автор темы не гадал.

Значения конкретного пользователя в админке отдельно не редактируются:
их правят на странице профиля этого пользователя (§5) — там уже есть форма,
права и аудит.

## 9. Миграции

- Одна новая append-only миграция с timestamp больше `1780000000`
  (последняя на момент проверки — `1780000000_topic_description.go`).
  Применённую миграцию не править — только новая.
- Миграция создаёт `profile_field_definitions` и `profile_field_values`
  (все правила `nil`), индексы (`key` unique, `(user_id, field_id)` unique)
  и расширяет словарь `roles.permissions` новым ключом
  `manage_profile_fields` + сверяет системные роли
  (по образцу `1769500000_mention_all_permission.go`).
- Сидов нет: форум стартует без кастомных полей, первое создаёт админ.
  Тесты — по образцу `1769400000_profile_permission_repair_test.go` /
  `identity_test.go`: словарь прав и системные роли не расходятся с
  `internal/auth`.

## 10. Что НЕ входит в v1

- Встраивание сторонних страниц (`iframe`, в т.ч. YouTube-плеер) — только в v2,
  отдельным allowlist доверенных доменов; в v1 видео — только прямой файл
  по URL через `<video>`. Причина: `iframe` — это чужая страница целиком,
  а не тег, и пускать его по одному allowlist с `div` нельзя.
- `details` / `summary` (сворачиваемые блоки) — кандидат в allowlist v2,
  если понадобится.
- Обязательные поля (в т.ч. при регистрации) — в v1 все поля необязательны.
- Валидация по регулярному выражению / значение по умолчанию — v2.
- Поля на уровне маски (персонажа), а не аккаунта — v2, отдельной сущностью.
- Поиск/фильтр участников по значению поля, показ полей в списке участников — v2.
- История изменений значений (кроме аудита правок сотрудником, §3.3) — v2.

## 11. Открытые вопросы (с дефолтами, принятыми в концепте)

1. **HTML как значение:** решено 2026-11-16 — да, тип `html` в v1, рендер только
   через allowlist-санитайзер (§7.1), включая `audio` / `video` / `source`.
   Осталось решить: нужен ли в будущем `iframe` (YouTube и подобные) —
   дефолт: нет, только в v2 с allowlist доверенных доменов.
2. **Дефолтная видимость нового поля:** `all` (включая гостей) или `members`?
   Дефолт концепта — `all`, как у подписи, которая уже публична.
3. **Подписи полей:** двуязычные `{en, ru}`, как `forumName`, или пока только
   русский? Дефолт — двуязычные.
4. **Кто создаёт поля:** только chief admin / root или любой админ с
   `manage_profile_fields` (право можно выдать кастомной роли)? Дефолт — право
   выдаётся, по умолчанию у chief admin / root.
5. **Нужны ли поля на уровне маски** (у каждого персонажа свои), или аккаунта
   хватает? Дефолт — аккаунта хватает, маски — v2.
6. **Показывать ли поле в списке участников / поиске?** Дефолт — нет, только
   профиль и посты.

## 12. Приёмка

- [ ] Админ без `manage_profile_fields` не видит вкладку; с правом — создаёт
  поле, `key` после создания не меняется.
- [ ] Поле с `show_in_profile = true` видно в «О себе», с `false` — нет;
  то же для `show_in_posts` в карточке автора.
- [ ] Гость видит только `visibility = all`; залогиненный без нужной роли
  не видит поле с `visibility = roles`; владелец с ролью вне списка не видит
  своё же поле ни в профиле, ни в форме редактирования.
- [ ] Владелец правит своё поле при `owner_can_edit = true`, получает 403
  при `false`; чужое значение правит только держатель `edit_others_profile`,
  правка пишется в `audit_logs`.
- [ ] Неизвестный `key` в запросе значений — 400; `javascript:`-ссылка — 400;
  пустая строка стирает значение.
- [ ] Значение типа `html` с `<script>`, `<iframe>`, `onerror=`, `javascript:`-ссылкой,
  `style`-атрибутом и `autoplay` рендерится без них (тег/атрибут вырезан,
  остальное на месте); `<audio controls>` и `<video>` с `source` рендерятся;
  тот же allowlist действует в профиле и в постах.
- [ ] Значение, поменянное в профиле, сразу новое во всех старых постах
  (без пересохранения постов); страница темы делает не больше одного
  дополнительного запроса на всех авторов страницы.
- [ ] `ESLint`, `go vet ./internal/platform/pocketbase/`, `npm run build` —
  зелёные; новая миграция применяется на чистой базе и не трогает старые.
