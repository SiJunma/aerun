# Концепция: Серверный локатор постов (Post Locator & Page Renderer)

**Статус:** Утверждено и зафиксировано  
**Стек:** Go (PocketBase) + SQLite + React (Frontend)  

**Главная цель:** Избавиться от клиентского перебора страниц или лишних сетевых вызовов при переходе по прямой ссылке на конкретный пост (`topic_id` + `post_id`). Локатор должен за один единственный запрос на сервере вычислить точную страницу поста через SQL `COUNT` и сразу вернуть пачку постов для рендеринга.

---

## 0. Находка (комментарий человека)
При миграции с Firebase серверная функция locatePost была перенесена на клиентсайд и использовала sequence постов. Мы избавились от этого параметра из-за дороговизны перерасчета порядка при хард удалении постов. В этот момент агент решил пойти костыльным путем и сделал перебор каждой страницы через вызов с клиента, чтобы отыскать нужный айди поста. 
Этот подход - отвратительный по всем логичным соображениям, особенно когда постов в теме может быть 2-3 тысячи. 

**Далее идет концепт от веб-агента, который просто пытался помочь описать план работы с функцией по словам человека, реальный код он не знает.**

## 1. Проблема
В больших темах (до 2–3+ тысяч постов) клиентский поиск поста путем последовательного запроса страниц или загрузки всей темы создает огромный сетевой мусор и лаги. Прежний подход разделял вычисление страницы и загрузку данных на два отдельных шага, что приводило к лишним кругам до сервера.

## 2. Архитектурное решение (Single Request Pattern)
Бэкенд на Go принимает `topicId` и `postId`, после чего:
1. Находит целевой пост для верификации и получения его метки времени (`created`).
2. Быстро вычисляет порядковый номер поста и нужную страницу через оптимизированный SQL-запрос.
3. Сразу забирает из базы нужную порцию постов для этой страницы с учетом глобальной настройки пагинации (`perPage`).
4. Возвращает клиенту и номер страницы, и готовый список записей (`items`) в одном JSON-ответе.

---

## 3. Детальный алгоритм работы на сервере (Go)

### Шаг 1: Валидация и поиск базовых данных
* Получить параметры `topicId` и `postId` из query-строки.
* Запросить у базы целевой пост по его `id`, убедиться, что он принадлежит указанному `topic_id`.
* Извлечь точное время создания поста (`created`), так как именно по нему строится хронологический порядок постов в теме (`created ASC`).

### Шаг 2: Расчет позиции и страницы через SQL `COUNT`
Чтобы не тянуть в память тысячи записей, мы просим SQLite сразу выдать количество постов, которые идут «до или вместе» с целевым:
```sql
SELECT COUNT(*) 
FROM posts 
WHERE topic_id = {:topicId} AND created <= {:created}
```
* Полученное значение `totalBefore` представляет собой порядковый номер поста (начиная с 1).
* Вычисление индекса (с нуля): `targetIndex = totalBefore - 1`.
* Вычисление номера страницы (при размере страницы `perPage`, например, 20):  
  $$\text{page} = \lfloor \frac{\text{targetIndex}}{\text{perPage}} \rfloor + 1$$

### Шаг 3: Выборка постов страницы
Используя вычисленный номер страницы и `perPage`, бэкенд формирует SQL-выборку:
```go
offset := (page - 1) * perPage
// SELECT * FROM posts WHERE topic_id = ? ORDER BY created ASC LIMIT perPage OFFSET offset
```

### Шаг 4: Ответ клиенту
Эндпоинт отдает готовый JSON:
```json
{
  "page": 4,
  "post_index": 65,
  "per_page": 20,
  "target_id": "zxg675bwvwox048",
  "items": [
    // Массив объектов постов для страницы 4
  ]
}
```

---

## 4. Обязательные требования к базе данных (Индексация)
Для того чтобы `COUNT` и хронологическая пагинация работали за микросекунды даже при 10 000+ постов в теме, в коллекции `posts` необходим составной индекс:
```sql
CREATE INDEX idx_topic_created ON posts (topic_id, created);
```

---

## 5. Поведение на клиенте
1. Пользователь кликает по ссылке-якорю на конкретный пост.
2. Фронтенд отправляет **единственный** запрос:  
   `GET /api/aerun/posts/locate?topicId=...&postId=...`
3. Получив в ответе номер страницы и массив `items`, клиент мгновенно монтирует нужную страницу темы и инициирует плавный скролл к целевому посту по его `id`.
