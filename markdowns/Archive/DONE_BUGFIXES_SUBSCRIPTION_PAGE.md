## 0. Что сломано (симптомы с продакшена)

1. На странице `/subscriptions` у темы «[25.04.2026] По разные стороны тени» горит оранжевый индикатор непрочитанного, хотя непрочитанных сообщений нет. На главной и в «Активных темах / Новых ответах» та же тема непрочитанной НЕ помечена.
2. Порядок тем на странице не совпадает с порядком в ответе сервера: первая тема из ответа (`I like to move it`, последний пост 11 Sep 2026) рендерится последней.
3. В ответе сервера нет поля `per_page`, как у других списков, — размер страницы будто бы не синхронизирован с глобальной настройкой «тем на странице».
4. В кнопке «На главную» внизу страницы подписок нет стрелки `←` (на остальных списках она есть).
5. Отдельно: цвет имени автора в `.author-meta__name` берётся из `--author-date-color` (цвет даты), хотя должен быть цветом имени.

## 1. Причина главного бага (пункт 0.1) — проверено по коду

Цепочка такая:

- Сервер считает тему непрочитанной по своему состоянию `topic_read_states` (предикат `unreadTopicsPredicate`, `backend/internal/platform/pocketbase/notifications.go`). Для темы из симптома сервер считает её прочитанной: она НЕ входит в `unreadTopicIDs`, поэтому на главной и в ленте новых ответов точка не горит.
- Для списков тем бэкенд уже отдаёт серверный флаг построчно: `listTopicsHandler` (`backend/internal/platform/pocketbase/forum_topics.go:580-602`) один раз резолвит `unreadTopicIDs` и ставит `items[i]["unread"] = unreadSet[r.Id]`. Комментарий там же прямо описывает этот сбой: карта прочтений на клиенте может расходиться с сервером — «a topic read server-side but stale locally keeps its dot forever».
- Но обработчик подписок `listUserSubscriptionsHandler` (`backend/internal/platform/pocketbase/subscriptions.go:164`) этого НЕ делает: вложенные темы собираются через `loadVisibleTopics` → `topicPayload`, а `topicPayload` поле `unread` не ставит вообще. В ответе сервера `unread` отсутствует — проверено по реальному ответу.
- На фронтенде `TopicRow` (`src/components/common/TopicRow.jsx`) при отсутствии флага делает так: `serverUnread = null` → `isUnreadByServer = true` (по умолчанию) — и точка зависит только от локальной карты прочтений `readMap`. А `readMap` — это per-device карта в `localStorage` (`subscribeToReadMap`, `src/api/auth-resources.js:179`), она отстаёт от сервера (другой браузер, «прочитать всё», запись старше последнего поста). Для этой темы локальная запись старше `last_post_created` 2026-10-17 23:03 UTC — поэтому точка горит только на подписках.
- Почему горит ТОЛЬКО одна тема, а не все четыре: у остальных трёх последний пост — от самой Alina (через персонажа Kyle Haze), а `TopicRow` не считает непрочитанным пост от себя (`topic.last_post_author_ref?.user_id !== user?.uid`). Это маскировка, а не норма.

Вывод: чинить надо бэкенд подписок (добавить серверный флаг), а не логику `TopicRow` и не `readMap`.

## 2. Исправление A — серверный флаг `unread` в подписках (главное)

**Файлы:** `backend/internal/platform/pocketbase/subscriptions.go` (обработчик `listUserSubscriptionsHandler`, строка 164; вложение тем — `loadVisibleTopics`, строка 291).

Для гостя поле оставить отсутствующим (гость сюда не попадает — обработчик требует авторизацию, но правило то же: нет мнения сервера — нет поля).

4. На фронтенде ничего менять НЕ нужно: `normalizeTopic` (`src/api/forum.js:11-30`) копирует тему спредом `...t`, поэтому `unread` переживёт нормализацию, а `TopicRow` уже предпочитает серверный флаг локальной карте.

**Проверка:**

- (ручная проверка человеком) У темы с реально непрочитанным ответом — `"unread": true`, точка горит.
- (ручная проверка человеком) Гость / разлогин — поведение как раньше (обработчик требует авторизацию, страница показывает пустое состояние).

## 3. Исправление B — сортировка «сначала новые» должна жить на сервере

**Файлы:** `backend/internal/platform/pocketbase/subscriptions.go` (строка 222), `src/api/subscriptions.js` (`fetchUserSubscribedTopics`), `src/api/forum.js` (`normalizeTopic`).

**Что не так:**

- Сервер упорядочивает подписки по `created DESC` (дата подписки, строка 222), а клиент пересортирует уже полученную страницу по `last_post_at_ms` (`src/api/subscriptions.js`: `validTopics.sort((a, b) => (b.last_post_at_ms || 0) - (a.last_post_at_ms || 0))`). Поэтому порядок ответа и порядок на экране расходятся — это нормально для одной страницы, но ломается на нескольких: сортировка действует только внутри страницы, и тема с более свежим постом со второй страницы встанет после более старых с первой. Плюс клиентская сортировка противоречит курсору пагинации, который построен по дате подписки (`created|id`).
- Дополнительно: `last_post_at_ms` / `created_at_ms` в `normalizeTopic` (`src/api/forum.js:26,29`) считаются через голый `new Date(...)`. Даты PocketBase имеют вид `"2026-10-17 23:03:12.268Z"` — с пробелом вместо `T`. V8 такой формат понимает и `Z` учитывает, а другие движки могут прочитать время как локальное — сдвиг до 4 часов, неверный порядок сортировки. В проекте для этого уже есть `toMillis` (`src/utils/dates.js`), который пробел нормализует.

**Шаги:**

1. В `listUserSubscriptionsHandler` упорядочить выборку по активности темы, а не по дате подписки: JOIN таблицы тем по `topic_id`, `ORDER BY topics.last_post_created DESC, topics.id DESC`. Сортировка должна произойти В ЗАПРОСЕ (в SQL), а не в Go после выборки — сортировка уже выбранной страницы проблему межстраничного порядка не решает.
2. Курсор пагинации привести к форме активности (`last_post_created|id`) — по образцу курсоров `listTopicsHandler` (`forum_topics.go`: форма `last_post_created|id` для лент без пинов). Номерной путь (`?page=`) при этом продолжает работать через OFFSET поверх того же порядка.
3. После серверной сортировки УБРАТЬ клиентскую сортировку в `fetchUserSubscribedTopics` — один источник порядка. Оставить комментарий, что порядок задаёт сервер.
4. В `normalizeTopic` считать `created_at_ms` и `last_post_at_ms` через `toMillis` из `src/utils/dates.js` вместо голого `new Date(...).getTime()`. `dates.js` ни от кого не зависит, циклических импортов не будет. Поведение для нормальных дат не меняется, для пробельной формы становится одинаковым во всех движках.

**Проверка:**

- Подписки с перемежающейся активностью на двух страницах: глобальный порядок «сначала новые» держится через границу страниц; порядок в ответе сервера совпадает с порядком на экране.
- Пагинация `?page=2` не теряет и не дублирует темы.
- Сортировка в Chrome и в другом движке (или unit-проверка `toMillis` на строке с пробелом) даёт один и тот же порядок.

## 4. Исправление C — `per_page` в ответе подписок

**Проверка:** ответ подписок содержит `per_page`, равный числу строк на странице; при смене настройки «тем на странице» число строк и число страниц меняются согласованно.

## 10. Слияние `feature/theming` в `main` (2026-11-17)

**Что сделано:** `git merge feature/theming` выполнено в `main`. Слияние прошло автоматически стратегией `ort`, за исключением одного нюанса, зафиксированного в пункте 5 этого документа.

**Нюанс мержа (цвет имени автора):** на `feature/theming` два блока `.author-meta__name` уже были слиты в один (коммит `b8f36780`), и в этом слитом блоке оставалось устаревшее значение `color: var(--author-date-color, var(--author-meta-color))`. На `main` после фикса E в том же блоке стояло `color: var(--author-name-color, var(--text-color))`. Автомерж оставил версию из `feature/theming` — иначе говоря, исправление E с `main` перетерлось бы слиянием.

**Разрешение:** в файле `src/styles/author-meta.css` в единственном блоке `.author-meta__name` явно проставлено `color: var(--author-name-color, var(--text-color))` — имя автора красится цветом имени, а не даты. Дата (`.author-meta__date>span`, строка 45) осталась на `--author-date-color`, как и было.

**Проверка после мержа:**
- `npm run build` — зелёно.
- `author-meta.css` строка 113 — `var(--author-name-color, var(--text-color))`.
- Все фиксы A–E (`subscriptions.go`, `forum.js`, `subscriptions.js`, `SubscriptionsPage.jsx`, `DraftsPage.jsx`) сохранены, не перетерты мержам.
