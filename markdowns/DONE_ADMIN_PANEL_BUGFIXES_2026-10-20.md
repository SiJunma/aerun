## 2. Находки

### A1. Бейдж root в таблице участников больше бейджа администратора

`src/pages/AdminPage.jsx`, `renderUsers()`, ветка chief-admin:

```jsx
<Badge bg={visuals.color} className={`role-badge px-3 ...`} style={{ fontSize: '0.85rem' }}>
```

Ветка обычной роли (там же, строкой ниже):

```jsx
<Badge bg={visuals.color} className={`role-badge px-2 ...`} style={{ fontSize: '0.8rem' }}>
```

Разница ровно в двух величинах: горизонтальный отступ (`px-3` = 1rem против `px-2` = 0.5rem) и
кегль (`0.85rem` против `0.8rem`). Это инлайновые стили, поэтому `.role-badge` из `src/index.css`
(`padding: .2rem .75rem; font-size: .75rem`) их не перекрывает.

Итог: бейдж главного администратора выглядит как увеличенный бейдж администратора — ровно то
«различие», которое и смущает. При этом сам root рисуется визуалами роли `admin`
(`getRoleVisuals('admin', roles)`), то есть по смыслу это ТОТ ЖЕ бейдж, только раздутый.

**Решение:** метрики главного администратора приравниваются к метрикам администратора
(`px-2`, `0.8rem`), а дополнительное отличие выносится в отдельный класс `badge-root` — хук для
кастомизации, который не меняет размер и не влияет на бейдж администратора.

### A2. Кнопка «Передать роль» показывается не тому, кто владеет ролью

Корень — в том, КАК клиент определяет «я главный администратор».

`src/pages/AdminPage.jsx:72`:

```js
const isSelfRoot = isChiefAdmin(user?.email, user?.role_id);
```

`user` — это auth-снимок из `AuthProvider` (`{ uid, id, email, displayName, photoURL, providerData }`).
**Поля `role_id` у него нет вообще**, поэтому `user?.role_id === undefined`, и весь ответ даёт
вторая ветка `isChiefAdmin`:

```js
export const isChiefAdmin = (userEmail, roleId) =>
  userEmail === import.meta.env.VITE_ADMIN_EMAIL || roleId === CHIEF_ADMIN_ID;
```

То есть «я root» определяется по ПОЧТЕ, а не по роли. Сценарий владельца:

1. Бывший root отдаёт роль (`POST /admin/transfer-root`). Сервер честно переводит его в `admin`.
2. Клиент этого не знает: его почта по-прежнему совпадает с `VITE_ADMIN_EMAIL` → `isSelfRoot === true`
   → кнопка «Передать роль» продолжает рисоваться на строке НОВОГО root'а (тот самый баг из репорта).
3. Новый root, наоборот, своей кнопки не получает: его почта не совпадает с `VITE_ADMIN_EMAIL`, а
   `role_id` в auth-снимке отсутствует → `isSelfRoot === false` (вторая половина репорта).

Дополнительно: `isChiefAdmin` сравнивает почту с `import.meta.env.VITE_ADMIN_EMAIL` БЕЗ проверки,
что переменная вообще задана. Если в сборке её нет, `undefined === undefined` → `true`, и главным
администратором считается вообще любой, у кого нет почты.

Тот же почтовый резерв переехал в `resolveUserRoleId` (`src/constants/permissions.js`) — то есть
бейдж бывшего root в публичных местах тоже рисуется как root.

**Решение:** главный администратор определяется РОЛЬЮ, а почта остаётся резервом только на случай,
когда роли нет (неизвестный/старый DTO). То есть `roleId` задан → ответ по роли; роль не задана →
после этого допускается почтовый fallback. Бонусом чинится «admin без root-бейджа» в публичных видах.

### A3. Подтверждение удаления не называет пользователя

`src/pages/AdminPage.jsx`, `handleDeleteUser(uid)`:

```js
message: t('admin.users.confirm_delete_message'),
```

Текст общий: «Вы уверены, что хотите навсегда удалить этот аккаунт?». В модалке сразу несколько
действий (удалить аккаунт / удалить все посты), и нигде не сказано, КОГО удаляют. Ник участника
доступен в той же строке таблицы (`u.nickname`), но в диалог не попадает.

**Решение:** в текст подтверждения подставляется ник цели, отдельным ключом словаря с
плейсхолдером `{nickname}`; при пустом нике подставляется «Без имени» (тот же запасной текст, что
и в таблице).

### A5. Интерфейс предлагает смену роли, которую сервер отвергает

Серверная матрица — `checkRoleChange` в
`backend/internal/platform/pocketbase/admin_users.go` (это и есть «функционал», которому должен
соответствовать интерфейс):

| Актор | Что сервер разрешает | Что сервер отвергает |
|---|---|---|
| `root` | любую цель | запись роли `root` (роль только передаётся) |
| `admin` | цель со **строго меньшим** рангом; роль `admin` назначить нельзя | свою роль и роль равного admin'а («strictly below yours»); назначение `admin` («only the chief admin may appoint an administrator») |
| прочие | — | всё («only an administrator or the chief admin may change roles») |

Ранги (сервер, `backend/internal/auth/role.go`): root 1000, admin 800, moderator 600, player 400,
spectator 300, guest 200. Для кастомных ролей ранг берётся из строки реестра.

Клиентская часть этому не соответствует:

* бейдж роли в таблице кликабелен для ЛЮБОЙ не-root строки, если есть право `change_roles`
  (а у admin'а оно есть по умолчанию) → админ открывает модалку смены роли **у себя** (A5) и у
  другого admin'а, хотя сервер отвергнет оба запроса;
* список ролей в модалке — `roles.filter(r => r.id !== 'root')`, то есть там есть `admin`, которую
  admin-актор назначить не может.

**Решение:** клиентская проверка становится зеркалом серверной:

* менять роль могут только `admin` и `root` (как в `checkRoleChange`: `actor != admin && actor != root`
  → отказ) — при наличии права `change_roles`;
* `admin` — только у аккаунтов со строго меньшим рангом (свой и равные admin'ы исключены
  автоматически);
* `root` — у любого, кроме root-строки (она и так защищена);
* список назначаемых ролей исключает `root` всегда, а `admin` — только если актор не root.

Ранги считаются тем же способом, что и на сервере: для системных ролей — скомпилированные значения,
для кастомных — ранг строки реестра (публичный `GET /roles` его публикует).

## 6. Доработка: редактор ролей (Н1)

По решению владельца Н1 («тоже чини, это ведь баг админки») взята в работу. К пункту A5 она относится напрямую: интерфейс не должен ни отказывать в том, что сервер примет, ни предлагать то, что сервер отвергнет.

### 6.1. Находки

**Н1а. Ранг сравнивался по двум несуществующим полям.** `canEditRole` сравнивал ранг «своего» role с рангом целевого:

```js
const myRole = roles.find((r) => r.id === user?.role_id);   // user.role_id НЕТ в auth-снимке
const myRoleLevel = myRole?.level ?? ROLE_LEVELS[user?.role_id] ?? 0;   // .level нет в реестре
const targetRoleLevel = targetRole.level ?? ROLE_LEVELS[targetRole.id] ?? 0;
return myRoleLevel > targetRoleLevel;
```

`user` — auth-снимок `{ uid, email, displayName, ... }`, **роли в нём нет**. Реестр публикует `rank`, а не `level`. Поэтому `myRoleLevel` всегда был 0, и `0 > 90` — false: **админ не мог отредактировать ни одной роли**, включая те, что сервер принимал без вопросов. Плюс `ROLE_LEVELS` в самом `AdminPage` — вторая локальная таблица рангов (100/90/50/…), расходящаяся с серверной (1000/800/600/…).

**Серверная правда.** `run.go`: `PATCH/POST/DELETE /roles` привязаны к `RequirePermission(auth.PermManageRoles)` — **ранговой проверки там нет вообще**. `catalog_roles.go` комментирует это прямо: «Roles are data the admin owns: a system role is edited exactly like a custom one». Строка `root` из таблицы ролей и вовсе не показывается (фильтр `r.id !== 'root'`), так что «редактор ролей» и кабинет главного администратора не пересекаются.

**Н1б (главная опасность).** Просто снять блокировку было бы нельзя. Форма сидится так:

```js
const allowedForRole = MAX_ROLE_PERMISSIONS[role.id] || [];   // у КАСТОМНОЙ роли такой записи НЕТ
permissions: normalizePermissions(role.permissions || []).filter(p => allowedForRole.includes(p)),
```

Для кастомной роли `MAX_ROLE_PERMISSIONS[role.id]` → `undefined` → `[]` → **в форме не отмечено ни одного права**. Сохранение такой роли писало пустой набор прав: права кастомной роли стирались открытием её же редактора и нажатием «Сохранить». Разблокировка кнопки без этой правки превратила бы «серые кнопки» в «админ может тихо обнулить роль».

### 6.2. Что сделано

| Что | Решение |
|---|---|
| **Серверная матрица** | `canEditRole` теперь = право `manage_roles` и ничего больше — ровно то, что требует сервер. Сравнение рангов и локальная таблица `ROLE_LEVELS` удалены: серверной ранговой проверки для ролей нет, а вторая копия чисел расходилась с первой. |
| **Сид формы** | Форма стартует с прав, которые роль **хранит**, минус ключи, которых сервер не знает (иначе `PATCH` отвечает 400 и роль становится нередактируемой). Потолок роли больше не режет набор — он применяется там, где и должен: в списке чекбоксов. |
| **Список чекбоксов** | Право, которое роль уже держит, показывается **даже если оно выше потолка**. Иначе оно было бы невидимым — а невидимое право нельзя ни снять, ни учесть. Потолок теперь ограничивает, что можно **добавить**, а хранимое — что **видно**. |
| **Проверка** | `scripts/check-admin-role-authority.mjs` фиксирует: роль-редактор гейтится на `manage_roles`; `ROLE_LEVELS` в панели больше нет; clamp `MAX_ROLE_PERMISSIONS[role.id]` не возвращается; фильтр неизвестных ключей на месте; хранимые права остаются видимыми. |

**Побочно.** Кнопка «Удалить» у роли использует тот же `canEditRole` — теперь она активна у админа, как и требует сервер (он отказывает только для системных ролей, а такая кнопка и не рисуется — `!role.is_system`).

## 7. Живая проверка

Автотесты закрывают форму кода, но не форму интерфейса: половина дефектов видна только в
работающей панели. Сценарий — по пунктам отчёта.

### 7.1. A1 — бейдж главного администратора

1. Войти под **главным администратором**, открыть `/admin` → «Участники».
2. Сравнить бейдж в строке root с бейджем в строке обычного администратора: **шрифт и отступы
   должны совпадать**. Различия в оттенке/цвете — это и есть отметка «Root» (класс `badge-root`).
3. Бейдж в строке root должен быть того же размера, что и у всех остальных ролей в таблице.

### 7.2. A2 — передача роли

Нужен **второй аккаунт** (кандидат) и аккаунт, который передан роль.

1. Под root: «Участники» → в строке root есть кнопка «Передать роль».
2. Передать роль кандидату. После передачи:
   - **у прежнего root** кнопки «Передать роль» быть НЕ должно (он теперь обычный админ);
   - **у нового root** кнопка «Передать роль» должна быть (роль теперь его);
   - в строке нового root — бейдж «Защищённый», и он по-прежнему защищён.
3. Проверить в **публичных** местах (доска участников, профиль): прежний root рисуется как
   «Администратор», а не как «Главный администратор».

### 7.3. A3 — подтверждение удаления

1. «Участники» → «Удалить» у любого участника.
2. В модалке текст должен **называть участника по нику**.
3. Чекбокс «Удалить все посты этого пользователя» и пояснение к нему должны быть **внутри
   модалки** (раньше рисовались за её backdrop'ом и были недостижимы).

### 7.4. A5 — смена роли

Под **админом** (не root):

1. Кликнуть по бейджу роли **у себя** → редактор открываться НЕ должен (сервер такой запрос
   отвергает: «strictly below yours»).
2. То же у другого админа → редактор не открывается.
3. Кликнуть по бейджу роли у **модератора/игрока** → редактор открывается, роль меняется.
4. В списке ролей модалки у админа **нет пункта «Администратор»** (назначить админа может
   только root) и **нет «Главный администратор»** (роль только передаётся).

### 7.5. Редактор ролей (вкладка «Роли»)

Под **админом** (не root):

1. Кнопки «Изменить» / «Удалить» у ролей должны быть **активны** (сервер такие записи принимает).
2. Открыть редактор **кастомной** роли: все её права должны быть **отмечены** (раньше форма
   открывалась пустой, и сохранение стирало права роли).
3. Сохранить без изменений → права роли **не изменились**. Это главная проверка: до правки
   сохранение обнуляло права кастомной роли.
4. Снять галочку с права → при сохранении право уходит; поставить обратно → возвращается.
5. Право, которого роль уже держит, но которое выше её потолка, должно быть **видно** (иначе его
   нельзя снять) — но новые права выше потолка предлагаться не должны.
