# CONCEPT: Кастомизация смайликов — админский модуль и свои смайлы пользователя

Ветка: `main`. Статус: концепт для исполнителя (задача на реализацию, не отчёт).

Скриншот-референс — панель стикеров с другого форума (группы-вкладки
EMOJI / CURSED / PIXEL / … / СВОИ, поле «Url стикера», кнопки «+» и
«карандаш», у каждого стикера крестик удаления). Референс задаёт только
внешний вид панели; поведение — по разделам ниже, и оно местами намеренно
отличается от референса (см. §4.3).

## 1. Цель

Один модуль вместо захардкоженных наборов:

- **(A) Админка:** дефолтные наборы смайликов настраиваются через группы —
  создавать группы, загружать в них картинки прямо в админке, удалять
  лишнее, включать/выключать.
- **(B) Пользователь:** кнопка «Свои смайлы» — свои наборы по группам,
  картинки хранятся как ссылки, которые приносит сам пользователь.
- **(C) Безопасность от случайного удаления:** контролы удаления своих
  стикеров видны только в режиме редактирования (см. §4.3).

## 2. Текущее состояние (проверено по коду ветки `main`)

- Наборы захардкожены в `src/config/smiles.js`: `SMILE_PACKS` — три пака:
  `jcdragon` (~60 gif, `/smiles/jcdragon/…`), `possum` (7 png),
  `tumblr` (~90 gif). `ALL_SMILES_MAP` строится из них (`code → url`).
- Рендер в постах и ЛС — `src/components/common/BBCode.jsx`: коды вида
  `[jcdragon]` заменяются на `<img>`; коды сортируются по убыванию длины,
  чтобы длинные не перебивались короткими.
- Пикер — `src/components/common/SmilesPicker.jsx`: вкладки
  `react-bootstrap` (`Tabs`/`Tab`), инлайн-стили, Bootstrap-классы
  (`p-2`, `d-flex`, `gap-2` и т.п.). Своих смайлов нет, админки нет,
  удаления нет. Чистка пикера от инлайна и Bootstrap — скоуп спринта G;
  данный модуль затрагивает пикер заново (новые вкладки и режим
  редактирования), поэтому его миграцию на семантические классы делать в
  рамках модуля, а не отдельным заходом.
- Загрузка файлов на сервере уже есть как прецедент (загрузка аватара,
  файловые поля PocketBase). Отдельных коллекций для смайлов нет.

## 3. Решения (принятые по умолчанию; спорные — на усмотрение заказчика)

1. **Хранение дефолтных наборов — две новые коллекции PocketBase** (а не
   поле в настройках): файлы — это файловые поля, а группы и порядок —
   отдельные записи. См. §4.1.
2. **Существующие три пака мигрируют в БД сидом** с теми же кодами и
   текущими URL (`/smiles/…`); файлы пока остаются в публичной папке.
   Новые загрузки администратора — уже файловые поля PocketBase.
3. **Свои смайлы пользователя — только ссылки** (без загрузки файлов):
   пользователь вставляет URL картинки, он сохраняется как есть. См. §4.2.
4. **Код смайла** — короткий текст в квадратных скобках, как сейчас
   (`[possumhappy]`). У пользователя код либо задаётся им самим, либо
   генерируется (`[uXXXX]`); уникальность — в пределах одного пользователя.
5. **Лимиты (предложение, решает заказчик):** до 50 своих смайлов на
   пользователя, до 20 в одной группе; URL — только `http(s)`, только
   картинки (`png`/`jpg`/`jpeg`/`gif`/`webp`), длина до 2048 символов.
   Админские загрузки — до 5 МБ на файл.

## 4. Реализация

### 4.1. (A) Админский модуль дефолтных наборов

**Коллекции PocketBase (новые):**

- `smile_groups`: `name` (text), `key`/`slug` (text, уникальный,
  латиница), `sort_order` (number), `enabled` (bool, по умолчанию true).
- `smile_items`: `group` (relation → `smile_groups`, cascade delete),
  `code` (text, уникальный глобально — совпадение с существующим кодом
  отклоняется), `image` (file, single, картинки), `sort_order` (number),
  `enabled` (bool, по умолчанию true).

**Миграция-сид:** создать группы `jcdragon`, `possum`, `tumblr` и записи
с существующими кодами и URL из `src/config/smiles.js`. После сида
`smiles.js` как источник данных удаляется: фронт получает дефолтные
наборы с сервера (см. §4.4).

**Админка — новая вкладка «Смайлы»** (вкладки админки — через конфиг
навигации, по итогам реорга админки):

- список групп с порядком (drag или кнопки вверх/вниз), создание /
  переименование / удаление группы (удаление группы удаляет и её смайлы,
  с подтверждением);
- внутри группы: сетка смайлов, загрузка картинки прямо в админке
  (input file → файловое поле PocketBase), код подставляется из имени
  файла и правится вручную; удаление лишнего смайла — с подтверждением;
- переключатель `enabled` у группы и у смайла (выключенное не отдаётся
  фронту, но не удаляется);
- минимум одна включённая группа должна оставаться — полностью пустой
  пикер недопустим (проверка на сервере и в UI);
- все тексты — через i18n (EN + RU); новый код — без `react-bootstrap`,
  без инлайн-стилей и Bootstrap-утилит, цвета через переменные темы.

**Права:** только админ (та же проверка, что у остальных вкладок админки).

### 4.2. (B) Свои смайлы пользователя

**Коллекция PocketBase (новая):**

- `user_smiles`: `owner` (relation → `users`, обязательное), `group_name`
  (text, по умолчанию «Свои»), `image_url` (url), `code` (text),
  `sort_order` (number), `created` (autodate).
- API-правила: list/create/update/delete — только `owner` равен
  текущему пользователю (`@request.auth.id = owner`); для гостей —
  ничего. Уникальность `code` — в пределах одного `owner` (проверять на
  сервере при создании; дубликат отклоняется с понятной ошибкой).
- Удаление пользователя удаляет и его смайлы; в старых постах коды
  остаются текстом (существующий fallback в `BBCode.jsx`).
- Валидация URL на сервере при сохранении: схема только `http`/`https`,
  расширение картинки, длина ≤ 2048. `javascript:`/`data:`-URL отклонять.

**Пикер (`SmilesPicker`):**

- Вкладки: дефолтные группы из §4.1 + вкладка «Свои» (отдельная группа,
  по умолчанию активна последней; группы пользователя — отдельные
  вкладки, если он создал больше одной).
- Вкладка «Свои»: поле «Url стикера» + кнопка «+» добавляют смайл в
  текущую группу пользователя; код — из поля кода рядом (или
  автогенерация, если поле пустое); превью картинки до сохранения.
- Гость видит только дефолтные группы; вкладка «Свои» гостю не
  показывается.

### 4.3. (C) Режим редактирования — защита от случайного удаления

Это прямое требование заказчика: сейчас на референсе крестики удаления
висят на каждом стикере всегда, и стикеры удаляются случайно.

- Кнопка-карандаш на вкладке «Свои» включает/выключает **режим
  редактирования** (состояние — только в пикере, не сохраняется).
- **Вне режима редактирования:** никаких крестиков, поля URL и кнопки
  «+» нет. Клик по стикеру вставляет его код в текст. Панель выглядит
  как обычная сетка смайлов.
- **В режиме редактирования:** на каждом своём стикере появляется крестик
  удаления; показываются поле «Url стикера», кнопка «+», переименование
  группы и удаление группы. Клик по стикеру в этом режиме ничего не
  вставляет.
- Удаление своего стикера или группы — **с подтверждением** (диалог
  «Удалить?»), даже в режиме редактирования.
- Выход из режима редактирования — повторный клик по карандашу либо
  закрытие пикера; при закрытии режим сбрасывается.
- У дефолтных (админских) групп контролов удаления для пользователя нет
  вообще — ни в каком режиме.

### 4.4. Рендер и единый источник данных

1. Фронт при загрузке приложения (или при первом открытии пикера —
   на усмотрение исполнителя, но один раз за сессию) запрашивает
   дефолтные наборы с сервера (`enabled` группы и смайлы, по
   `sort_order`) и строит из них карту `code → url` той же формы, что
   нынешняя `ALL_SMILES_MAP`. После успешной загрузки `src/config
   /smiles.js` удаляется; `BBCode.jsx` и `SmilesPicker.jsx` читают карту
   из одного места (контекст или стор — как принято в проекте).
2. Свои смайлы авторизованного пользователя подгружаются отдельно и
   **дописываются в ту же карту** (коды пользователя не пересекаются с
   дефолтными — при коллизии побеждает дефолтный код, а пользовательский
   смайл не рендерится и помечается в пикере). После любого изменения
   своих смайлов карта перестраивается без перезагрузки страницы.
3. `BBCode.jsx`: логика подмены не меняется — сортировка кодов по
   убыванию длины, `<img>` с `alt=code`, `loading="lazy"`. Внешние URL
   своих смайлов рендерятся как есть; битые ссылки — `onError` скрывает
   картинку, а не ломает пост (поведение согласовать с текущим рендером
   картинок в BBCode).
4. Свои коды работают везде, где рендерится BBCode (посты и ЛС), а не
   только в месте, где открыт пикер.

## 5. Проверки

- `npm run build` и `npm test` — зелёные.
- Админ: создать группу, загрузить 2 картинки, переименовать группу,
  выключить смайл (пропал из пикера), удалить смайл (с подтверждением),
  удалить группу (с подтверждением, смайлы ушли вместе с ней).
- Пользователь: добавить свой смайл по URL, вставить его код в пост
  (картинка видна в посте и в ЛС), создать вторую группу, удалить смайл.
- Вне режима редактирования на своих стикерах нет крестиков, поля URL и
  «+»; клик вставляет код. В режиме редактирования крестики есть,
  удаление спрашивает подтверждение.
- Дубликат кода (свой = дефолтному или второй такой же свой) отклоняется
  с понятной ошибкой; `javascript:`-URL отклоняется.
- Гость: вкладки только дефолтные, «Свои» нет; чужие смайлы не видны и не
  подставляются.
- Сид: после миграции в пикере те же три пака с теми же кодами, что были
  в `smiles.js`; старые посты с `[jcdragon]` и т.п. рендерятся как раньше.
- В новом коде нет импортов `react-bootstrap`, инлайн-стилей и
  Bootstrap-утилит (проверить grep'ом по новым/изменённым файлам).

## 6. Вне скоупа

- Загрузка файлов для своих смайлов пользователя (только ссылки).
- Магазин/обмен наборами между пользователями.
- Анимация/предпросмотр гифок в админской сетке сверх превью картинки.
- Миграция файлов существующих паков из публичной папки в файловые поля
  (остаются URL; перенос — отдельной задачей, если понадобится).

## 7. Порядок работ

1. Сервер: коллекции `smile_groups` / `smile_items` / `user_smiles`,
   эндпоинты CRUD + загрузка файла + проверка уникальности кода.
2. Админка: вкладка «Смайлы», группы, загрузка/удаление, переключатели
   `enabled`.
3. Сид трёх существующих наборов, удаление `src/config/smiles.js` как
   источника данных.
4. Пикер: вкладка «Свои», свои группы, добавление по ссылке, превью до
   сохранения.
5. Режим редактирования (крестики только в нём, удаление — с
   подтверждением).
6. Проверки (§5).
