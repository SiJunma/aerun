# Documentation Maintenance Rule

Правила поддержания документации проекта в актуальности (BMAD-подход: документация — часть кода, а не приложение к нему).

## 1. Инвентарь и владение

| Документ | Статус | Когда обновлять |
|----------|--------|-----------------|
| `PROJECT_CONTEXT.md` | живой | при изменении бизнес-правил, фич, архитектурных решений |
| `PROJECT_SPEC.md` | живой | при изменении схемы БД, API, RBAC, жизненного цикла сущностей |
| `backend/README.md` | живой | при изменении запуска, окружения, CI, миграций |
| `DEPLOY.md` / `backend/deploy/README.md` | живой | при изменении деплоя/топологии |
| `.agent/rules/*.md` | живые | при изменении правил работы |
| `markdowns/SPEC_*.md`, `TODO_*.md` | по фиче | при работе над соответствующей фичей |
| `markdowns/Archive/` | архив | сюда попадают закрытые документы |

## 2. Правило синхронизации (главное)

**Любое изменение кода, которое меняет контракт, обновляет соответствующую документацию в том же коммите/PR:**

- миграция схемы → `PROJECT_SPEC.md` §1 (+ новая строка миграции не требует отдельных записей — таблица описывает текущее состояние);
- новый/изменённый маршрут `/api/aerun/*` → `PROJECT_SPEC.md` §3;
- изменение прав (`permission.go`, роли, правила категорий) → `PROJECT_SPEC.md` §2 и, при необходимости, `PROJECT_CONTEXT.md` §4;
- изменение бизнес-правила (семантика удаления, идемпотентность, presence, почта) → `PROJECT_CONTEXT.md` §4;
- изменение деплоя/окружения → `DEPLOY.md` / `backend/deploy/README.md`.

Если агент не может обновить документацию (недостаточно данных) — он обязан зафиксировать это в отчёте по задаче, а не оставить документ молча устаревшей.

## 3. Жизненный цикл рабочих документов в `markdowns/`

- Именование: `CONCEPT_*` (идея) → `SPEC_*` (спецификация) → `TODO_*` (план работ) → `DONE_*` / `CLOSED_*` (завершено, префикс + дата) → перенос в `markdowns/Archive/`.
- Завершённые и отменённые документы **не удаляются**, а архивируются с префиксом `DONE_`, `CLOSED_` или `ARCHIVE_`.
- Устаревший документ, который нельзя удалить (на него могут ссылаться), помечается блоком:
  ```
  > ⚠️ **ОТРЕДАКТИВНО / <причина>**
  > [что именно устарело и почему]
  > Актуальная документация: [ссылки]
  ```
  плюс ярлык в заголовке: `# Название [ОТРЕДАКТИВНО / <причина>]`.

## 4. Гигиена ссылок и дат

- **Не ссылаться на несуществующие пути.** Перед записью ссылки — проверить, что файл существует (включая `.agent/rules/*`, `markdowns/Archive/*`). Если документ переехал в архив — ссылаться на архивный путь.
- Каждый живой документ несёт в шапке дату актуальности и статус. При существенном пересмотре — обновить дату.
- Текущая ветка/стек/версии указывать только те, что подтверждены кодом (`go.mod`, `package.json`, `git branch`), а не по памяти.

## 5. Источники истины (не дублировать, а ссылаться)

- Схема БД → миграции `backend/internal/migrations/` (полные списки полей); `PROJECT_SPEC.md` даёт обзор.
- API → `backend/internal/platform/pocketbase/run.go`.
- Права → `backend/internal/auth/permission.go`.
- Состояние CI → ветка `ci-report` (`git show origin/ci-report:report.json`).
- Запуск/окружение → `backend/README.md`.

Документы описывают и интерпретируют эти источники, но не копируют их дословно: копия устареет раньше источника.

## 6. Проверка перед завершением задачи

Агент, завершающий задачу, отвечает на чек-лист:
1. Изменил ли я контракт (схему/API/права/деплой)? Если да — обновил ли `PROJECT_SPEC.md` / `PROJECT_CONTEXT.md` / `DEPLOY.md`?
2. Все ли ссылки, которые я добавил, существуют?
3. Не оставил ли я в живых документах утверждений, противоречащих коду?
4. Если план/документ завершён — перенесён ли он в `markdowns/Archive/` с нужным префиксом?

## 7. Известные исторические ловушки (не повторять)

- Описание стека «по памяти» — легаси-Firebase описание месяцами путало агентов; стек подтверждать по `go.mod`/`package.json`.
- Ссылки на `PROJECT_CONTEXT.md`/`PROJECT_SPEC.md` до их создания — проверять существование файла перед предписанием его обновить.
- Ссылки на документы в корне репозитория, которые уже переехали в `markdowns/Archive/` (например, инцидент пост-удаления).
