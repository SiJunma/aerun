# Project Rules

> **Актуально** для стека **Go 1.27 + PocketBase (SQLite) + React 19** (обновлено 2026-11-02).
> Контекст продукта: `PROJECT_CONTEXT.md`. Схема БД / API / права: `PROJECT_SPEC.md`.
> Правила поддержания документации: `.agent/rules/documentation_maintenance.md`.
> Firebase-эпоха живёт в ветке `legacy-firebase` — читать как историю, не как спецификацию; её файлы помечены `⚠️ ОТРЕДАКТИВНО`.

- **User instruction precedence**: The agent configuration file (`.agent/rules/AGENTS.md`, `.clinerules`) holds standing defaults and guardrails, not absolute prohibitions. When the human gives an explicit instruction that contradicts a default rule, the explicit instruction takes precedence — the human is the authority and knows what they asked for. Defaults exist to prevent *unwanted autonomous* action, not to veto an explicit, intentional command from the human.

- **Build and Deployment Workflow**: Two distinct workflows, not one rule:
  - On `main` (current production branch: Go + PocketBase, deployed via `deploy.py`, see `DEPLOY.md`), building and deploying is a routine, explicitly-requested operator workflow. When the human explicitly asks to build or deploy, that explicit request overrides this file's general "do not"-style wording and the agent performs it. If the human does not ask, the agent stays out of it and does not touch the database.
  - The Firebase-era branch is `legacy-firebase` (archived, never deployed). Treat it as read-only history; do not deploy from it. (Updated 2026-11-02: the earlier wording called `main` a live Firebase branch — that is no longer true; the Firebase→PocketBase migration work has landed on `main`.)
- **PocketBase-first Data Architecture**: SQLite (PocketBase) — единственный источник истины. Динамические данные (presence, счётчики непрочитанного, realtime-сигналы) обслуживает Go-слой команд: presence — через heartbeat-маршруты `/api/aerun/presence/*`, realtime — SSE-сигналы + polling-fallback через `src/api/shared-poll.js`. Не вводить вторую «живую» БД: эпоха Firebase RTDB закончена; файлы с именами `rtdb-*.js` в `src/api/` носят исторические имена и работают через PocketBase.
- **Presence считается от последнего клика, не от heartbeat-тика**: «онлайн» = 15 минут после последнего клика/нажатия клавиши, одинаково для открытой и закрытой вкладки (закрытие вкладки гостя не удаляет — нет pagehide-beacon; явный leave только при логине/разлогине). Клиент передаёт `last_active_at` в heartbeat; сервер клампит его в окно `[now−15m, now]` (stale → краю окна, не к `now` — иначе давно ушедший гость воскресает одним битом). `users.last_seen` = время последнего клика (троттлинг 5 мин; при выбывании по таймауту — точный момент клика, не момент выбывания). Изменения состава онлайна — SSE `presence.update` (debounce, без данных) + перечитывание `GET /status`.
- **Documentation Maintenance**: Whenever modifying database schemas, API methods, permissions, or data flows, agents MUST update the corresponding documentation files (`PROJECT_CONTEXT.md`, `PROJECT_SPEC.md`) in the same commit. Full rules, document lifecycle and the pre-completion checklist: `.agent/rules/documentation_maintenance.md`. Before starting work, verify documentation accuracy against the code and prune outdated or misleading sections.
- **Deny-by-default Permission Model**: Браузер не имеет прямого пути записи в коллекции (правила коллекций закрыты — superuser-only); все мутации идут через команды `/api/aerun/*`, которые через AccessResolver-middleware разрешают роль + статус + права. Права — строковые ключи в `backend/internal/auth/permission.go` (реестр `allPermissions`); смена роли уважает rank-матрицу, root-роль передаётся только через `POST /admin/transfer-root`. Статус аккаунта сужает права: `pending` → `view_forum` + self-edit, `banned` → ничего. Отсутствующая запись права — deny, никогда не allow.
- **Network & Connection Resilience**: Never render blank screens (`return null`) or unhandled infinite loaders on data fetch failures or connection drops. Always provide human-friendly fallback cards (`ErrorCard`) with retry buttons, copyable technical error details for reporting to admins, and clear neutral explanations of connection issues.
- **Zero Silent Failures & Diagnostic Transparency**: Never leave errors or exceptions without descriptive explanations or dead-end branching. Every failed operation, missing data state, or edge-case must have a meaningful user-facing notification (`Toast` / `Alert` / `ErrorCard`) and an informative diagnostic log for administrator troubleshooting.
- **Backend Verification Channel (CI report)**: For any change under `backend/**`, never assume local success is enough. Every push is verified on a clean Linux runner by `.github/workflows/backend.yml` (gofmt, `go build`, `go vet`, `go test`), which publishes a machine-readable result that agents must read with plain git: `git fetch origin ci-report` then `git show origin/ci-report:report.json` (schema `aerun-ci-report/1`; a check appears with `ok` only when that step ran and passed, so a missing key means failed/skipped; only the newest run is stored, history lives behind `run_url`). Fix red checks before starting new work. Full description: `markdowns/Archive/DONE_BACKEND_MIGRATION_AUDIT_AND_SPRINT_PLAN.md` §5 "Continuous verification channel" and `backend/README.md` §CI.
- **Deletion Must Settle Its Denormalized Copies (2026-09-30 incident)**: Flagging a row deleted is NOT the end of a delete. Production deleted a whole topic and left post counts, reputation votes and topic subscriptions all pointing at content that no longer existed — the forum kept showing members scores for posts nobody could read. Whenever you write or review a handler that deletes, hides, or moves content: (1) enumerate every denormalized copy of that content (counters, votes, subscriptions, caches) and decide explicitly for each — moved, paid back, or deliberately kept; (2) put the cleanup in the SAME transaction as the tombstone, never a follow-up step; (3) aggregate per author/target BEFORE mutating, and never early-`return` out of a decrement — the original bug was a per-post loop that bailed out because its parent row was already gone, so nothing was ever decremented; (4) make any reputation payout exactly-once by construction, not with an "already reverted" marker, and prove it by replaying with a DIFFERENT idempotency key; (5) keep `RecomputeUserCounters` and the command layer deriving the same value — the repair tool silently undoes fixes whose predicate it disagrees with; (6) do not hard-delete what a soft delete is meant to preserve. Worked examples and the full rule set: `markdowns/Archive/CLOSED_INCIDENT_POST_DELETE_WIPED_TOPIC.md` §"Rules for agents" (read before touching any delete path).

### Deploy key clarification

The GitHub Deploy Key `aerun_deploy.pub` authenticates the deploy machine toward GitHub (so it can clone the repo via SSH). It does NOT give the agent SSH access to the VPS. This agent runs on the dev machine, which has no SSH credentials configured here, so the agent cannot open an SSH session to the VPS itself. Real deployment is done by the human operator (or the deploy machine's own automation) from the deploy machine. I can build the frontend/backend artifacts, prepare the exact commands, and verify them locally, but the `scp`/`ssh` transfer and `systemctl restart` steps must be run from the deploy machine (home machine) or by operator automation.

When running on an office/secondary machine without the SSH key: the agent MUST NOT attempt deployment. Instead, the agent's job is strictly to: (1) verify code, (2) run local tests/builds, and (3) push commits to GitHub. Deployment to VPS is exclusively triggered from the primary home machine where the SSH key resides.

- **Never Edit a Definition Block and a Use in the Same Hunk (2026-09-25 regression)**: `src/api/dm-cache.js` lost five constants (`DM_CACHE_PREFIX`, `DM_CACHE_BUILD_KEY`, `MAX_CACHED_MESSAGES`, `CURRENT_BUILD`, `getCacheKey`) when a rewrite of `reviveTimestamp` took the declaration block above it with it. Every *call site* survived, so the file looked complete, and the module threw `ReferenceError` on the first `localStorage` touch — including `clearAllDmCache()` on signOut. It stayed invisible for a month because a `/* global __APP_BUILD_TIME__ */` comment was silencing `no-undef` and making the file read as deliberate. Two rules follow: (a) when a refactor removes an import or a construct at the top of a module, re-read the whole file afterwards — the diff's context lines are not the whole file, and a large hunk can silently absorb neighbouring declarations; (b) a definition is only proven by something dereferencing it, so a module with runtime behaviour gets a test that *executes* it, not one that reads it (`scripts/check-dm-cache-constants.mjs`, wired into `npm test`). Same shape as the delete rule above: the surviving evidence and the broken thing look identical until something uses it.
- **Tightening a predicate invalidates fixtures that only looked real**: `sumVotes` began resolving a vote's visibility through its post row, and `TestRecomputeUserCountersSumsEveryVote` failed — not because the rule was wrong, but because its fixture voted on post ids (`postmissing001`) that existed in no table. When you change a WHERE clause or a counting rule, grep the tests for fixtures that fabricate identifiers and re-check that they still satisfy the new predicate; a fixture that passes for the wrong reason is worse than one that fails.
- **When the codebase contradicts the plan, ASK — verify against the legacy app first (2026-10-01)**: if the running code feels like a different principle than the migration plan or the audit document describes, do not resolve it alone and do not "fix" the legacy behaviour to match the plan. Check what the Firestore implementation actually did, then ask the owner which principle wins, and say plainly which file you read. An audit that confidently documents a divergence produces a *new* wrong decision that is harder to unpick than the one it was reviewing, because the next reader trusts the doc over the code. Concretely, this cost two rewrites: a soft-delete tombstone (the plan implied reversibility; the owner wanted MyBB/Firestore hard delete) and a per-post `sequence` ordinal plus cursor pagination and `by-sequence` deep links (a plan optimisation; the legacy app had none of it and sorted by `created`). Both were defended with reasoning and tests, and both were still wrong — they were additions nobody asked for. Ask early; ask with the legacy behaviour in hand, not with an argument.
- **A subscription is not a timer, and it is not a resource (2026-10-03 network audit)**: every `subscribeToX` used to build its own `setInterval` AND its own PocketBase realtime channel, with nothing shared between callers — so one open topic page ran three identical `GET /me/notifications?limit=100` loops (tab badge, Notifications page, quote highlighting) plus a fourth "admin" one that was the same endpoint with the same account id, and two `GET /me/unread-counts` (AuthProvider and TitleProvider). A member paid for the same read N times. Two rules: (a) subscribe through `src/api/shared-poll.js` (`sharedPoll(name, …)`), never with a bare `setInterval` — the name is the resource identity, so a second caller costs zero requests, triggers coalesce onto one debounced read, only one request is ever in flight, and nothing polls a hidden tab; (b) two `/me/...` reads are the SAME resource if the server scopes both to the caller — never "fan out" by inventing an admin/legacy variant of a caller-scoped list, which reads as a feature and is really a duplicate poll plus, usually, rows rendered twice. Because these bugs are COUNTING bugs, they are invisible in review: gate a change here with a test that counts requests (`scripts/test-shared-poll.mjs`), never one that greps for the call.
- **Deletion is HARD for posts and topics; SOFT (tombstone) for direct messages**: the owner drew the line. A deleted topic or post is not listed, not numbered, not counted and not recoverable — matching the Firestore era and MyBB; the audit log is the only surviving record. A deleted DM is the opposite: it is a conversation, so both participants must keep seeing that a message was there and what it said, exactly as in a messenger. Do not generalise one into the other.
